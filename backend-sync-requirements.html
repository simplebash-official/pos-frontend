Backend Requirements — Offline Sync

JANA2U POS · Backend specification

What the backend has to provide for offline sync

The frontend sync engine is built and running against the inventory domain. It works today in a degraded mode — correct, but wasteful and unable to detect conflicts. This is everything the Rust/Axum backend needs to add to close that gap, in the order it should be built.

Scope inventory, suppliers, purchases, auth Consumers multiple terminals, multiple locations Client state engine live, degraded mode

00

The contract, in short

Each terminal keeps a full local copy of the data it needs in IndexedDB. Screens read that copy, never the network, so the shop keeps selling through a power cut. Writes are applied locally and queued in a durable outbox that replays to you when the connection returns.

That design puts three demands on the server. It must be safe to replay a write whose response was lost. It must be possible to ask what changed since a point in time, rather than re-downloading everything. And it must be the authority on anything two terminals can race on — stock levels, unique barcodes, sequential numbers.

What "degraded mode" means today

With none of this in place the engine still works: it re-downloads whole collections instead of deltas, sends no concurrency tokens, and cannot tell a genuine conflict from a normal failure. Every item below can land independently — nothing needs a big-bang release.

01

Blocking — problems that exist today

SYNC-01P0

Accept an Idempotency-Key on every mutating request

This is the single most important item on the page. A terminal in a shop with bad power will regularly send a request that succeeds on your side while the response never gets back. The client cannot tell that apart from a request that never arrived, so it retries — and without this, the retry creates a second product, a second stock intake, a second purchase.

Every POST, PUT, PATCH and DELETE carries the header. The rules:

  • Key on (user, Idempotency-Key). The client sends a UUID that stays constant across every retry of the same logical operation.
  • First time: run the operation, then store the status code and the exact response body.
  • Repeat with the same key: return the stored status and body verbatim. Do not re-execute. Add Idempotency-Replayed: true so the client can log it.
  • Same key, different request body: reject with 422 IDEMPOTENCY_KEY_REUSED. This catches client bugs rather than hiding them.
  • Same key while the first is still running: 409 IDEMPOTENCY_IN_PROGRESS with Retry-After: 1. The client treats it as a transient failure and backs off.
  • Retain records for 7 days, then expire.
Acceptance test

Kill the network after the request leaves the client but before the response returns. When the queue retries, exactly one row must exist on the server.

SYNC-02P0

Add collection endpoints — the client is currently making one request per row

Three resources have no "list everything" endpoint, only per-parent filters. To build its local copy the client has to fan out, and the cost is bad and grows with your data:

Resource What the client does now Requests Needed
Stock movements Loops every product, calls /inventory/products/:id/movements 1 per product GET /inventory/stock-movements
Supplier links Loops every supplier, calls /supplier-products?supplierKey= 1 per supplier GET /supplier-products
Purchases Loops every supplier, calls /purchases?supplierKey= 1 per supplier GET /purchases

With the 80 products currently in the database, one stock-movement refresh is 80 sequential HTTP calls. Each of the three needs an unfiltered, paginated variant returning the same shape as the filtered one, with the existing filters staying optional.

Give all three the same envelope the product list already uses — items plus a pagination object — and support page and limit. A limit of 500 should be accepted.

SYNC-03P0

Be the authority on stock, and reject overselling

The client keeps stock as your last known figure plus a ledger of unsent deltas, so two terminals each selling one unit produce -1 and -1 rather than two conflicting totals. That part is safe. What is not safe is the last unit: both terminals think it is available, and nothing on the client can know otherwise.

PATCH /inventory/products/:id/stock must therefore apply the delta inside a transaction and reject it when the result would go negative: 

409 {
  "success": false,
  "message": "Only 1 unit of Screen Protector is left in stock.",
  "code": "INSUFFICIENT_STOCK",
  "details": { "available": 1, "requested": 3, "productId": "..." }
}

Do not require an If-Match on this endpoint. Deltas commute, so a version check would reject writes that are perfectly safe to apply.

SYNC-04P0

Make sessions survive a multi-day outage

A shop can be offline for a day or more. When it reconnects, the terminal has a queue of real sales to upload — and if the access token expired during the outage, every one of those requests fails with a 401.

The client handles this as gracefully as it can: on a 401 it pauses the queue rather than burning retries, so nothing is lost. But the cashier is then blocked until someone signs in again. Either give access tokens a lifetime comfortably longer than a plausible outage, or issue a refresh token that survives one.

Related: GET /auth/me must return 401 for a genuinely invalid token and never for a transient server problem. The client treats 401 as "signed out" and anything else as "try later", so a 401 on a database hiccup would log a cashier out mid-shift.

SYNC-05P0

Never issue a key beginning with local_

Rows created offline get a provisional id of the form local_<uuid> until they reach you. The client decides whether an id is real by testing that prefix, so the check is only sound if you never mint one. It costs nothing to guarantee — add it as an invariant wherever ids and keys are generated.

SYNC-06P0

Give purchases and supplier links real timestamps

stock_purchases has no created_at or updated_at at all, and supplier_products has only added_at. Nothing without a server-set updated_at can take part in incremental sync, because there is no way to ask what changed. These two tables are the blocking prerequisite for section 2.

On products, created_at and updated_at exist but are optional in the payload. Make them required and always present.

02

Delta sync and conflict detection

This group turns full re-downloads into incremental updates and lets the client tell a real conflict from an ordinary error. Build it as one piece of work — the pieces depend on each other.

SYNC-07P1

Four columns on every syncable table

Column Type Meaning
version bigint, not null Starts at 1, increments on every write to the row. The concurrency token.
created_at timestamptz, not null Server clock, never the client's.
updated_at timestamptz, not null Server clock. Set on every write, including a soft delete.
deleted_at timestamptz, null Soft delete. Null means live.

Add updated_by_device (text, nullable) too, populated from the X-Device-Id header. It costs one column and makes "which till changed this?" answerable when someone disputes a price.

Index (updated_at, id) on each table — that pair is the keyset the sync cursor rides on, and without the index the delta query degrades as history grows.

Applies to: products, categories, subcategories, suppliers, supplier_products, stock_purchases, stock_movements.

SYNC-08P1

Soft-delete everything, and keep tombstones for 90 days

A row deleted with DELETE FROM is invisible to an incremental query — the terminal never learns it went, keeps its local copy forever, and re-uploads references to it. Every delete endpoint must set deleted_at instead, and every read endpoint must filter deleted rows out by default.

Keep tombstones for 90 days, then purge. That retention window is exactly what makes a stale cursor unsafe, which is why the next item needs a rejection path.

SYNC-09P1

One endpoint that answers "what changed since?"

One multiplexed endpoint rather than one per resource. On a flaky connection, reconnect sync is where things die — six round trips each with TLS and auth is six chances to fail, and the cursors stay consistent with each other if they come back together. 

GET /sync/changes?cursors=products:c_MTcyMz…,categories:,suppliers:c_MTcy…&limit=500

# `cursors` is a comma-separated list of resource:cursor pairs.
# An EMPTY cursor means "I have nothing — send me a full snapshot".

200 {
  "success": true,
  "data": {
    "serverTime": "2026-08-09T11:23:44.812Z",
    "changes": {
      "products": {
        "full": false,
        "items":   [ { …entity, "version": 7, "updatedAt": "…" } ],
        "deleted": [ { "key": "prod_abc", "deletedAt": "…", "version": 4 } ],
        "nextCursor": "c_MTcyMzE5OTQyNDgxMnxwcm9kX3h5eg",
        "hasMore": false
      },
      "categories": { … }
    }
  }
}
  • The cursor is opaque to the client — encode (updated_at, id), not a bare timestamp, or rows written in the same millisecond get skipped.
  • Return rows ordered by (updated_at, id) ascending. The client applies them in order.
  • hasMore: true means the client immediately asks again for that resource only, until it drains.
  • A cursor older than the tombstone window is unsafe — reject it with 400 CURSOR_INVALID and the client falls back to a full snapshot automatically.

Also expose per-resource variants such as GET /inventory/products/changes?since=. The client uses them for targeted re-reads after a compound write, and they are the same query with one resource in it.

SYNC-10P1

Conditional writes, and one conflict response shape

Updates and deletes send If-Match: <version> — the version the edit was based on. If the stored version has moved, someone else changed the row first and the write must be refused rather than silently overwriting. 

409 {
  "success": false,
  "message": "This product was changed on another device.",
  "code": "VERSION_CONFLICT",
  "details": {
    "expectedVersion": 7,
    "serverVersion": 9,
    "updatedByDevice": "01JBQZ…",
    "server": { /* the full current row */ },
    "conflictingFields": ["sellingPriceCents", "name"]
  }
}

Returning the current row in details.server matters: it lets the terminal show a side-by-side comparison without a second request, which is the difference between a usable conflict screen and a dead end.

A missing If-Match means "no precondition" and should be allowed — that is how creates and legitimate force-writes arrive.

Watch this one

PUT /suppliers/:id is a full replace: fields left out get cleared. Two terminals editing different fields of the same supplier will silently wipe each other's work without a version check. This endpoint is the strongest argument for the whole item.

SYNC-11P1

A health endpoint and a server clock

navigator.onLine in the browser only reports whether a network cable is live — a terminal connected to a router with no upstream still reports "online". The client therefore probes you directly. 

GET /health          # no auth, no database access
200 { "ok": true }
Cache-Control: no-store
X-Server-Time: 2026-08-09T11:23:44.812Z

It must not touch the database. A server that is up but whose database is down should still answer, so the client can tell "unreachable" from "reachable but broken" and behave differently.

Send X-Server-Time on every response, not just this one. POS hardware runs for years with dying CMOS batteries and drifting clocks; comparing it against the terminal's own clock is how the app warns someone that records are being filed under the wrong time.

SYNC-12P1

Accept X-Device-Id on every request

Each terminal generates a stable id on first run and sends it on everything. Use it for the audit column, for conflict attribution, and later for number-block ownership. No behaviour needs to depend on it — just record it.

03

Later — when billing moves onto the engine

SYNC-13P2

Reserved number blocks for invoices and job tickets

Human-facing sequential numbers cannot be generated offline without collision. Two terminals offline at once will both issue INV-2026-0042. The repair and print-job numbers are worse: they are derived from how many rows exist, so deleting a job re-issues a number that is already on a printed ticket. 

POST /sequences/{name}/reserve      # name: invoice | repair | printJob
{ "deviceId": "01JB…", "count": 50 }

200 {
  "name": "invoice", "blockId": "01JB…",
  "prefix": "INV-2026-", "padding": 4,
  "start": 143, "end": 192,
  "expiresAt": "2026-09-08T00:00:00Z"
}

A terminal reserves a block while online and consumes it offline, topping up when it drops below about a fifth remaining. You must never re-issue a range. Unused numbers in an expired block are burned, not recycled — gaps in an invoice sequence are legal, duplicates are not.

SYNC-14P2

A batch push endpoint — only if measurement says so

The client currently replays queued writes one request at a time against your existing endpoints. That is deliberate: it needs no new server-side write paths, so none of the code that touches money and stock has to be rewritten, and every failure is attributable to one operation.

A POST /sync/push returning 207 Multi-Status is worth building only if reconnect flushes are measured taking longer than about ten seconds in the shop. Switching later is a change to one file on the client.

SYNC-15P2

Consider collapsing the dual id / key identity

Products and suppliers carry both an id used in URLs and a key used for cross-feature links. The client has to track and remap both, and every reference has to declare which one it holds. If the backend accepted key everywhere a path currently takes id, that whole class of bug disappears.

Not urgent, but it gets more expensive to change the longer it stays.

04

Error codes the client acts on

Errors keep the existing envelope — message, code, statusCode, details. The code is what the client branches on, so it must be stable and machine-readable; message is shown to a cashier and should read as plain language.

Code Status Client behaviour State
VERSION_CONFLICT 409 Per-resource policy: keep server copy, or ask a person New
INSUFFICIENT_STOCK 409 Flags the change for review; stock is re-read New
REFERENCE_NOT_FOUND 409 Change is held for a person to repoint or discard New
CURSOR_INVALID 400 Clears the cursor, falls back to a full snapshot New
IDEMPOTENCY_KEY_REUSED 422 Treated as a permanent failure — surfaces a client bug New
IDEMPOTENCY_IN_PROGRESS 409 Transient; retries with backoff New
BARCODE_ALREADY_EXISTS 409 Held for a person to resolve Exists
CATEGORY_ALREADY_EXISTS 409 Held for a person to resolve Exists

Status codes carry meaning of their own, independently of any code string. The client sorts them into four buckets, so getting them right matters more than the message:

Status Interpreted as Consequence
401 / 403 Session ended Queue pauses without consuming retries; user is asked to sign in
409 / 412 / 404 Conflict Routed through the resource's conflict policy
408 / 429 / 5xx Transient Retried with exponential backoff, up to eight attempts
Other 4xx Permanently invalid Rejected immediately and surfaced for a person to fix
One thing to avoid

Never return a 4xx for a temporary server-side problem. The client will treat it as permanently invalid, stop retrying, and put a real sale in front of a cashier as something they have to resolve by hand.

05

Operational notes

OPS-01P1

Expect a stampede when the power comes back

Every terminal in the area reconnects within the same few seconds, each with a queue to upload and a full sync to run. The client already spreads retries with randomised backoff, but plan capacity for the burst rather than the average, and prefer returning 429 with Retry-After over timing out — the client backs off cleanly on a 429 and handles a timeout much less gracefully.

OPS-02P1

Keep compound writes transactional

POST /inventory/products with a suppliers array creates the product, the supplier links, the purchase records and the stock movements in one call. The client deliberately queues that as a single operation, because your transaction is the atomicity boundary. If that ever became partially applied, the client would have no way to represent it.

The response returns only the product, so the client re-reads the related resources afterwards. Returning the created links and purchases in the response body would remove those follow-up requests, if that is easy to add.

OPS-03P2

Scheduled jobs

  • Purge idempotency records older than 7 days.
  • Purge tombstones older than 90 days.
  • Expire unconsumed number blocks past expiresAt, without recycling the numbers.
06

Acceptance

Each of these is verifiable from the terminal, and each corresponds to a failure that will otherwise show up as missing money or duplicated stock in a real shop.

  • Dropping the response to a product create, then retrying, leaves exactly one product.
  • A full sync of every resource is a bounded number of requests, not one per row.
  • Two terminals selling the last unit: one succeeds, one gets INSUFFICIENT_STOCK.
  • A terminal offline for a day reconnects and uploads its queue without re-authenticating.
  • Deleting a product on one terminal removes it from another within one sync cycle.
  • Two terminals editing the same supplier offline: the second gets VERSION_CONFLICT, not a silent overwrite.
  • A cursor older than the tombstone window returns CURSOR_INVALID and recovers on its own.
  • GET /health still answers when the database is down.
  • A second sync after an idle minute transfers nothing when nothing has changed.
