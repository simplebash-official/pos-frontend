# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A point-of-sale system for a repair/retail shop (billing, repairs, print jobs, inventory, customers, reports). React 19 + TypeScript + Vite, using Mantine 9 as the UI kit.

### Keep the two checkouts in sync (check before doing anything)

Every app repo exists **twice** on this machine: the working copy at `pos/<name>` (edit and commit here) and the pinned submodule at `pos/desktop/<name>` (what the desktop app and its installers build from). They drift apart, and when they do, features silently disappear from whichever one you run (the desktop's browser sign-in step once lived only in the pinned frontend, so a run from the working copy showed the old form).

**Before starting any task, compare them:**

```bash
git -C pos/<name> fetch ../desktop/<name>
git -C pos/<name> log --oneline HEAD..FETCH_HEAD     # in the pinned copy, missing here -> merge these in first
git -C pos/<name> log --oneline FETCH_HEAD..HEAD     # in the working copy, missing from the pin
git -C pos/desktop submodule status
```

- Pinned copy has commits the working copy lacks: `git merge <sha>` them into the working copy first (resolve conflicts, rerun the tests).
- Working copy is ahead: commit there, then move the pin: `git -C pos/desktop/<name> fetch ../../<name> && git -C pos/desktop/<name> checkout --detach <sha>`. Never edit files inside `pos/desktop/<name>` directly. Pushing (and the bump PR) is a separate, deliberate step.
- Never run `tauri dev` or build an installer while the working copy is behind the pin.
- Dev run of the desktop app against the local Docker stack: build with `CLOUD_API_URL=http://localhost:8082 CLOUD_SYNC_API_URL=http://localhost:8081` (read at compile time with `option_env!`; `touch pos/desktop/src-tauri/src/cloud/mod.rs` to force a rebuild). Use `:8081` for the Docker POS API: the Docker backend on `:8080` shares its port with the desktop's own sidecar, which answers first on loopback.

## Before finishing any task: test everything that can be tested

A task is not done until everything in this codebase that _can_ be tested, and everything related to the feature you implemented, has been tested and passes. Not just the lines you changed.

1. **The feature itself:** add or extend automated tests for every behaviour you added or changed (happy path, failure paths, edge cases), then run them.
2. **Everything around it:** run this repo's full suite and quality gates (below), not only the new tests. A change can break a caller far away.
3. **Across repos:** when a feature spans repos (backend, frontend, desktop shell, document-server, identity-server, app-frontend, deployment), run the gates in _every_ repo you touched, plus the tests that exercise the whole path end to end.
4. **For real:** what automated tests cannot reach (UI behaviour, a running stack, long-lived connections, a deploy) is verified by running it: the local Docker stack (`LOCAL_DOCKER_GUIDE.md` at the workspace root), the desktop app, or the browser.
5. **Match CI's toolchain:** CI uses the latest stable Rust/Node. A lint that passes on an older local toolchain can still fail there, so update (`rustup update`) or run the gate with CI's version before calling it done.
6. **Report honestly:** say what you ran and its result. Anything you could not test is named, with the reason, and never presented as passing. A suite that silently skips (e.g. no database configured) is not a passing suite.

**This repo's gate:** `npm run test:all && npm run format && npm run lint && npm run type-check && npm run build` (both Vitest and Jest; a new test must pass under both runners). Check UI changes in the running app at the widths listed under Responsive & mobile UI.

## Responsive & mobile UI

The app targets three layout tiers. `src/styles/theme.ts` defines **no** custom `breakpoints`, so Mantine 9's defaults apply: `xs` 36em/576px, `sm` 48em/768px, `md` 62em/992px, `lg` 75em/1200px, `xl` 88em/1408px. (Don't confuse these with `CONTAINER_SIZES` in `theme.ts` — those are `Container` size overrides, not breakpoints.)

| Tier      | Width                  | Shape                                       |
| --------- | ---------------------- | ------------------------------------------- |
| `mobile`  | below `sm` (768px)     | one full-screen region at a time            |
| `tablet`  | `sm`–`lg` (768–1199px) | two columns, the secondary one tab-switched |
| `desktop` | `lg`+ (1200px)         | the full multi-column layout                |

**Picking a tier**: use `useLayoutTier()` / `useIsMobile()` from `src/shared/hooks/useResponsive.tsx` — never call `useMediaQuery` with a hand-written query string, and never hard-code `768`/`1200` in a component. Both hooks read from a single `LayoutTierProvider` subscription (mounted once in `src/app/providers.tsx`, above the router) rather than opening their own `useMediaQuery` listener — with ~40 call sites, independent listeners meant one breakpoint crossing fired a synchronized re-render burst across the whole tree at the exact moment layout-dependent CSS transitions were trying to animate. The hook passes `getInitialValueInEffect: false` so the tier resolves on the first render; Mantine's default would flash the wrong layout for a frame. Its `below()` helper subtracts the same fraction Mantine's own `visibleFrom`/`hiddenFrom` do, so a JS tier check and a CSS `visibleFrom` on the same breakpoint always agree.

**JS switching vs CSS switching**: reach for `visibleFrom`/`hiddenFrom` for small, stateless bits of chrome (a badge, an icon button). Use the hook when the alternatives are whole stateful subtrees — CSS-only switching mounts _both_ branches, so refs, `ResizeObserver`s, autofocus effects and query subscriptions all run twice. `BillingRegions` (`src/features/billing/components/BillingRegions.tsx`) is the reference implementation of the JS approach.

**Rules for any new screen or component:**

- **Touch targets ≥44px** below `sm`. Desktop-density controls (32–40px icon buttons, `size="xs"` steppers, tight action rails) must grow on mobile — see `CartLineItem.tsx`'s `railWidth`/`rowMinHeight` pattern. Never place two destructive-adjacent targets under 44px side by side.
- **Inputs must be ≥16px font on mobile.** iOS Safari zooms the entire page when a smaller input takes focus and does not zoom back out. `AmountInput` already clamps this; do the same for any bare `TextInput`/`NumberInput` you style with an explicit `fontSize`.
- **Don't autofocus on mobile.** The soft keyboard covers the list or grid the input filters. Gate every autofocus/refocus behind `!isMobile` (`CatalogPanel`'s `keepScanInputFocused`, and the search fields in `ServiceJobPickerModal` / `CustomerPickerModal`).
- **Modals go `fullScreen={isMobile}`**, drawers go `size={isMobile ? '100%' : ...}`, and popovers must clamp their width (`width: 'min(280px, calc(100vw - 32px))'`). A fixed `mah={440}` scroll area should become a viewport-relative `'60vh'`.
- **Use `dvh`, not `vh`,** for anything that fills the screen — `vh` ignores the mobile browser URL bar and the bottom of the layout ends up under it. Where a `vh` fallback is needed for older engines, declare the pair in `src/styles/global.css` (see `.billing-root`); an inline React style object can only hold one value per property.
- **Never hard-code the header height.** Import `BILLING_HEADER_HEIGHT` / `SHELL_HEADER_HEIGHT` from `src/app/layout/constants.ts`; `AppShell` and the screens that size against it must read the same constant.
- **Keyboard affordances are desktop-only.** Hotkey hints baked into labels (`Jobs (F4)`, `Complete · … (F2)`, `Hold (Ctrl+H)`), the focus-mode toggle and the shortcuts modal entry are meaningless on touch — strip the hint from the label string (don't fork the JSX) and wrap the controls in `visibleFrom="sm"`. Leave the `keydown` listeners registered: they're harmless without a keyboard and keep external-keyboard tablets working.
- **Grid spans must follow the tier, not the viewport.** A `span={{ base: 6, sm: 4 }}` inside a column whose own width changes per tier resolves against the _viewport_, so it silently means something different in each layout. Derive the span from `useLayoutTier()` instead (`CatalogPanel`'s `productCardSpan`). The catalog's cards-per-row is measured from its scroll area's width (`useCatalogColumns`, `lib/catalogColumns.ts`), not taken from the tier.
- **Toggle buttons with state-dependent text must use fixed widths with `flexShrink: 0`.** When a button toggles its label text based on state (e.g. _"Expand All"_ / _"Collapse All"_, _"Low Stock Only"_ / _"Showing Low Stock"_), do not rely on auto width or `minWidth` alone — text length changes expand/contract the button and cause adjacent layout elements (like search `TextInput`s) to shift. Always set an explicit fixed width and `flexShrink: 0` (e.g., `style={{ width: 180, flexShrink: 0 }}`) so the button and surrounding row items stay completely fixed.
- **Print documents are exempt.** `src/shared/print/documents/` is fixed `mm`/`px` geometry on purpose. Make the _preview container_ scroll on both axes and scale the page down; never make the document itself fluid.
- **Rows inside a `ScrollArea` don't shrink on their own.** Mantine wraps ScrollArea content in a `display: table` element, which is sized to max-content — so `flex: 1; min-width: 0` and `lineClamp` have no effect and wide rows spill past the container instead of compressing. Pass `classNames={{ viewport: 'scrollarea-fluid-content' }}` (defined in `src/styles/global.css`) whenever the content should be bounded by the container rather than define its width.
- **The sidebar adapts to viewport _height_, not just width.** `useSidebarDensity` (`src/app/layout/sidebarDensity.ts`) measures the navbar against its own content with a `ResizeObserver` and steps `SIDEBAR_DENSITY_PRESETS` (`comfortable → compact → dense`) so the nav fits without an internal scrollbar while retaining uppercase group labels across tiers; the root `overflowY: 'auto'` is the floor below it. Each step re-measures in a layout effect (never an animation frame), so the settle finishes before paint and a rail ↔ full swap never shows an intermediate density; the rail root is pinned to `SHELL_NAVBAR_RAIL_WIDTH` so a bar held wider during the width transition cannot re-centre its icons. The sidebar is two regions in a `minHeight: 0` column: the `<nav>` list (`flex: '1 1 0'`, `overflowY: auto`, `.sidebar-scroll`, carries the density ref) is the only part that scrolls, and the footer strip (Settings / theme cycle button / Sign Out / collapse chevron) is `flexShrink: 0` below it, so it never scrolls away. On desktop the user can collapse the bar to the rail (`onToggleCollapse`, saved in `STORAGE_KEYS.SIDEBAR_COLLAPSED`; Billing, tablet and phone ignore it) and fold sections (`STORAGE_KEYS.SIDEBAR_FOLDED`; the section holding the open page never folds). `Sidebar.tsx` calls the hook once for both the full and rail layouts (`enabled = !isMobile`; mobile is a scrollable drawer and stays `comfortable`).
- **Chart containers must never use scrollbars (horizontal or vertical).** Wrap charts with `ChartCard` (`src/features/reports/components/ChartCard.tsx`) which enforces `overflow: 'hidden'`, `width: '100%'`, and `minWidth: 0`. Mantine/Recharts chart components (`AreaChart`, `BarChart`, `LineChart`, `CompositeChart`, `DonutChart`) dynamically resize to 100% width via Recharts `ResponsiveContainer`; setting `overflowX: 'auto'` or `overflow: auto` causes fractional subpixel differences to trigger persistent horizontal scrollbars.
- Mantine 9's `Grid` takes **`gap`**, not `gutter` (that was Mantine 7).

Verify with the real thing: `npm run dev`, then walk the full flow at 375, 414, 768, 1024, 1280 and 1920 — plus at least one pass in dark mode — and assert `document.documentElement.scrollWidth <= window.innerWidth` at every width.

## Animation performance

Every animation in the app must play smoothly — no dropped frames, no visible stutter. The rules below come from a real incident: navigating into the Billing screen appeared to make the left navbar "shrink" with a stuck animation. The actual cause wasn't anything billing-specific — it was `AppShell`'s own chrome transition (driven by `isBillingPage`) racing Billing's heavy first mount, worsened by an unrelated `left`-property animation and an app-wide re-render fan-out. Follow these rules so the same class of bug doesn't come back.

- **Use `framer-motion` for any animation that needs more than a CSS transition.** When something needs to move, appear, leave or change place with real motion (tab or panel swaps, a highlight that slides between items, lists that enter or exit, shared-element moves, drawer/modal content), use `framer-motion` (`motion.*`, `AnimatePresence`, `layoutId`) rather than hand-rolled keyframes or `setTimeout` class toggles. Plain hover/focus colour fades stay as CSS transitions. Everything above still applies: animate only `transform` and `opacity` (`layoutId` and `x`/`y`/`scale` are fine), always call `useReducedMotion()` and drop the movement (duration 0, no slide) when it is true, and keep a screen boundary snapping instead of animating. Reference implementation: `src/shared/components/drawer/AnimatedTabs.tsx` (a `layoutId` pill that glides between tabs, plus a direction-aware `AnimatePresence mode="wait"` panel; the direction is worked out while rendering) and `ListRow.tsx`. In jsdom tests set `MotionGlobalConfig.skipAnimations = true` (from `framer-motion`) so panels swap at once — `installDrawerTestEnv()` in `drawer/testEnv.ts` does it.
- **Shared motion kit — `src/shared/motion/` (import from `@/shared/motion`).** Start here before writing a new `motion.*`: `presets.ts` (`EASE`, `DURATION` 0.15/0.2 s, `SPRING`, `staggerDelay`, and `resolvePresets(reduced)`), `useMotionPresets()` (the presets already resolved for reduced motion), `FadeIn` (fade + 6 px rise on mount, optional `index` stagger capped at 8), `AnimatedNumber` (counts a figure to its new value with tabular digits; pass `formatMoney` and integer cents), `PresenceSwitch` (opacity cross-fade between loading / empty / content). Feel: subtle and fast, since this is a till. Mantine `Modal`/`Menu`/`Drawer` transitions are set once in `theme.ts` (`transitionProps`, with `respectReducedMotion: true`), so do not pass a `transitionProps` per modal. Used by `ListRow`, `RegisterSessionBadge`, `DenominationCounter`, `ZReportModal`, `PaymentPanel` (change due) and `LabelDesignsTab`.
- **Only animate `transform` and `opacity`.** Those are the only two CSS properties the browser can update on the compositor thread without a `layout`/`paint` pass. Never animate `left`/`top`/`right`/`bottom`/`width`/`height`/`padding`/`margin` — if something needs to slide or resize, animate a `transform: translate()`/`scale()` instead. `transform`'s percentage values resolve against the animated element's **own** box, not its parent, so sliding relative to a fluid parent needs the parent's pixel width measured via `ResizeObserver` first — see `AmountInput.tsx`'s mode-toggle slider and `CartPanel.tsx`'s scroll-affordance observer for the reference pattern.
- **A route/screen boundary should snap, not animate.** Entering/leaving a screen is a navigation, not a resize — if a screen change (e.g. `AppShell`'s billing-specific header height / navbar width / padding) drives a Mantine transition, suppress that transition for the one render where the boundary is crossed (see `AppShell.tsx`'s `isBillingBoundaryChange` render-time state adjustment), and only let it animate for genuine in-page dimension changes (a tier crossing, a focus-mode toggle). An animated chrome resize landing in the same frame as a heavy screen's first mount is what makes it look "stuck" — the main thread can't keep up with per-frame layout work while it's busy committing a large render tree. The one exception is the shell's side-bar width (standard page ↔ Billing, desktop ↔ tablet): the layout still reflows once at the new width, and `useShellWidthTransition` (`app/layout/`) then slides `Main` with a `transform` and wipes the navbar with a `clip-path` over ~220 ms — never `width`/`padding`/`margin`. It is off for reduced motion and on phones.
- **Never call `useMediaQuery` directly in a component.** Always go through `useLayoutTier()`/`useIsMobile()` (see **Responsive & mobile UI** above) — this isn't just about breakpoint consistency, it's what keeps a single breakpoint crossing from re-rendering dozens of components at once and colliding with whatever CSS transition is trying to animate that same dimension change.
- **The sidebar's active item is a shared `layoutId` pill, and `Main`'s padding does not animate.** `SidebarNavItem.tsx` renders one `motion.span` (`.sidebar-pill`) behind the active item in each layout (rail and full) that glides between items with the `AnimatedTabs` spring; the link's own active background is switched off (`.sidebar-link` in `global.css`). Mantine's `AppShell` never transitions the navbar's `width`, so it also transitioned `Main`'s `padding` for 200ms and the page slid after the bar had already snapped — `.mantine-AppShell-main { transition: none }` makes the page reflow once (`useShellWidthTransition` then adds the visual slide), while the navbar keeps its compositor-only `transform` slide (focus mode, mobile drawer). A rail ↔ full swap fades the new layout in (opacity only, no exit).
- **Don't pair a `@keyframes animation` with `transition: all` on the same element.** `transition: all` re-evaluates every animatable property on every style recalculation, which is redundant work when a keyframe animation is already running and nothing else on the element actually changes conditionally. Scope `transition` to the specific properties that do (e.g. `border-color 0.15s ease, box-shadow 0.15s ease`), or drop it entirely if nothing else changes — see `CatalogPanel.tsx`'s scan-bar `Paper` and `CartLineItem.tsx`'s flash-row `Paper`.
- **Debounce a `ResizeObserver` that drives re-renders during a window drag.** A `ResizeObserver` fires every frame while the user drags a window edge; if its callback calls `setState` that changes padding / gaps / element visibility, the subtree re-renders on every one of those frames and visibly shakes. `useSidebarDensity` (`src/app/layout/sidebarDensity.ts`) never changes the tier straight from an RO event — it only (re)arms a `SETTLE_DELAY` (120 ms) timer, so the tier is frozen mid-drag and settles **once**, in a ≤3-frame `requestAnimationFrame` step-sequence, after the drag stops. All the observer/timer/measurement state lives in a mutable ref box behind a **callback ref** (never React state), so re-attaching on a standard↔rail layout swap is clean and a density change can't feed a render synchronously back into the effect.

## UI copy — write for a non-technical shop user

**The person using this app runs a repair/retail shop; they are not a developer and may not be a native English speaker.** Every string that reaches the screen — labels, placeholders, helper text, empty states, validation messages, toast titles, tooltips, `aria-label`s — is written for them, not for us. This is a hard requirement on every UI change, the same as responsiveness.

- **No standards names, formats, or internals in user-facing text.** `EAN-13`, `GS1`, "internal prefix 20", "minted on save", `SKU` collision rules, `local_` ids, "delta", "cursor", "outbox", "idempotency" — none of it means anything to a shop owner. Say what the feature _does for them_: "Create a barcode for me" / "A scannable shop barcode is made when you save." Keep the technical term only where the user genuinely searches for it (`SKU` on a printed label), never as the explanation.
- **No developer/DB jargon as adjectives.** "Immutable" → "cannot be changed". "Validation error" → "Please check the …". "Vendor" → "Supplier" (pick one word for a concept and use it everywhere; don't alternate "Vendor / Supplier"). "Intake" → "Received".
- **Say plainly when something is optional, and when it repeats.** Any section that accepts one _or many_ rows must say so in its empty state, in plain words — e.g. the product form's supplier section reads "Add one supplier, or add several if you bought this item from more than one place. You can skip this." A user who doesn't know a section is repeatable will cram two suppliers into one row; a user who doesn't know it's optional will invent data to fill it. Once rows exist, keep pointing at the repeat affordance by name ("Add each supplier separately with 'Add Another Supplier'"), and number the rows for humans (`Supplier 1`, not `Supplier Batch #1`).
- **Validation messages say what to do, not what failed.** "A barcode should be 8 to 14 numbers, with no letters or spaces", not "must match /^\d{8,14}$/" or "invalid format". "This supplier is already added above", not "Duplicate vendor selected".
- **Prefer a short question or instruction as a heading** where it makes the intent obvious ("Who did you buy this from?"). Sentence case for helper text, full sentences with a full stop.
- Keep the `aria-label` in the same plain language as the visible label — screen-reader users get no benefit from the internal name.

`ProductFormModal.tsx`'s supplier and barcode blocks are the reference for the tone.

## Center modals — one visual family

Every center-opening `Modal` (as opposed to a `Drawer` side panel) follows the pattern set by `ProductFormModal.tsx` ("Add New Inventory Product") — new modals should default to this rather than inventing their own header/footer/color treatment:

```tsx
<Modal
  opened={opened}
  onClose={onClose}
  title={
    <Text fw={700} size="lg">
      {isEditing ? `Edit: ${entity.name}` : 'Add New X'}
    </Text>
  }
  size="lg"
  centered
  fullScreen={isMobile}
>
```

- **Title is plain text, no icon.** `<Text fw={700} size="lg">` — no leading `ThemeIcon`, no `Kbd` shortcut chip, no subtitle line under the title. If the title needs to carry an identifier, fold it into the string itself the way `ProductFormModal` does with `Edit: ${productToEdit.name}` (e.g. `A4InvoicePreviewModal`'s `Invoice Preview — {invoice.invoiceNumber}`) rather than adding a second line.
- **No `radius` prop.** `defaultRadius: 'md'` in `theme.ts` already applies; an explicit `radius="var(--mantine-radius-default)"` on a `Modal` (or any component) is redundant — omit it.
- **`centered` and `fullScreen={isMobile}` on every center modal**, no exceptions except very small (`size="sm"`) confirmation dialogs like `ConfirmDialog` — a full-screen sheet for a yes/no question is worse UX than a small centered overlay, so those get `centered` only.
- **Footer**: `<Group justify="flex-end" mt="md" gap="sm"><Button variant="default" onClick={onClose} disabled={loading}>Cancel</Button><Button type="submit" color="blue" loading={loading}>{isEditing ? 'Save Changes' : 'Create X'}</Button></Group>` — Cancel is always `variant="default"` (never `subtle`), the primary action is always `blue` (or omitted, since `primaryColor: 'blue'` is the theme default).
- **Section labels inside the body**: `<Text size="xs" fw={700} c="dimmed" tt="uppercase" style={{ letterSpacing: '0.05em' }}>Label</Text>`.
- **Brand/feature accents are `blue`**, not a color picked per feature (no per-module indigo/teal/orange). This does **not** apply to semantic colors that carry independent meaning: `green` for a profit/positive amount, `orange` for a warning `Alert`, `red` for a destructive action's `confirmColor` — those stay as-is.

There's no shared `<AppModal>` wrapper — every modal styles Mantine's `Modal` inline, consistent with the rest of the codebase's per-component styling. `ProductFormModal.tsx` is the reference implementation; `ConfirmDialog.tsx` is the reference for small confirmation dialogs.

## Right-side detail & profile drawers — one visual family

Every right-side drawer is built from the kit in `src/shared/components/drawer/` (import from its `index.ts`, never from a single file): Item Specifications, Customer, Supplier, Employee, Invoice, Activity-log entry and Held Sales. Do not hand-roll a `Drawer`/`Paper`/`Tabs` stack; start from `RichDrawer` and its parts.

```tsx
<RichDrawer
  data={entity}                     // last item is kept while the drawer slides shut
  opened={opened}
  onClose={handleClose}
  width="wide"                      // 'wide' ≈900px two columns · 'standard' ≈620px · 'narrow' ≈460px; phones are full-screen
  title={{ icon: <IconX size={20} />, text: t('… Profile'), subtitle: t('…') }}
  footer={(e) => <DrawerFooter start={<FooterDelete … />}><Button variant="default">Close</Button>…</DrawerFooter>}
>
  {(e) => (
    <DrawerGrid>
      <KpiStrip>…<KpiTile><Figure|RangeFigure/></KpiTile>…</KpiStrip>
      <DrawerRail><DrawerHero …/><DrawerAfter><DrawerCard label icon>…</DrawerCard></DrawerAfter></DrawerRail>
      <DrawerMain><AnimatedTabs tabs value onChange>{(tab) => panel}</AnimatedTabs></DrawerMain>
    </DrawerGrid>
  )}
</RichDrawer>
```

The parts: `RichDrawer` (shell, header, canvas, pinned footer), `DrawerGrid`/`DrawerRail`/`DrawerAfter`/`DrawerMain` (two columns that fold to one by the **drawer's own width** with a container query in `global.css`, `.rich-drawer-*`, not by the viewport; the left rail is sticky and its `DrawerAfter` cards drop below the main content when narrow), `KpiStrip`/`KpiTile`/`Figure`/`RangeFigure` (headline numbers across the top), `DrawerHero` + `IconTile` (tinted hero card), `DrawerCard` + `SectionLabel` + `InfoRow` (cards and rows; `InfoRow stacked` for long values such as an address or email), `AnimatedTabs` + `CountChip` (pill tabs with a gliding highlight), `ListRow` (divided list rows that enter with a small stagger), `IconAction` (tinted icon buttons), `CopyIconButton`, `DrawerFooter` + `FooterDelete`. Page canvas is `--bg-app`, cards are `--bg-card`, tokens only, light and dark.

Rules learned while building the family — follow them for any new drawer:

- **Section titles sit inside their card** (`DrawerCard label`), never as a loose label above a card, so both columns start flush.
- **Ranges are spelled out.** An amount range shows labelled `Lowest` / `Highest` lines (`RangeFigure`), never `Rs. 40 – Rs. 55` on one line; one amount shows once with its hint.
- **Plain text over badges.** An id is a small monospace line (`eyebrow`), a status is a coloured dot and word (`status`), a path is `A › B`, a list of tags is `a · b`. Do not add badges.
- **Forms:** real labels above the fields, one long field per full row (supplier or product select, reason, notes), short numeric fields in rows of two or three, a placeholder that cannot be clipped, Cancel `variant="default"`, primary `blue`. Quantities are whole numbers (`allowDecimal={false}`).
- **Icon actions** are `IconAction`: tinted 32px (44px on phones), 16px icons, 6px gap, blue to edit, red to remove, each with a tooltip and `aria-label`. A destructive footer action is `FooterDelete`, which becomes an icon on phones.
- **Tabs** are `AnimatedTabs` with a count chip where there is a count; keep them on one row at 390px. Anything that must never be hidden (for example an invoice's credit notes) stays on view in a card above the tabs, not inside a tab.
- **Do not show internal ids or keys** (item key, client key, invoice key, supplier key); show created / updated dates instead.
- Wording follows the UI-copy rules above ("Supplier", never "Vendor"); new strings go through `t()` and `si.json`.

Per drawer: Item (`ItemDetailDrawer`, wide) shows stock, selling, cost and profit with stock-by-price colours; Customer (wide) total purchases, balance due, invoices, repairs; Employee (wide) commission, work, revenue, default rule, with History / Split Rules / Login tabs; Supplier (wide) products, intakes, spend, last intake, with Products / Intake tabs; Invoice (wide) total, balance or change, items, with Items / Payments / Activity tabs, the Credit Notes card kept above them and the payment and void dialogs in `InvoicePaymentModal` / `InvoiceVoidModal`; Log entry (standard, single column); Held Sales (narrow list with animated cards). Admin-only parts stay hidden from staff. The parked `features/sync/SyncDrawer` is dead code and not part of the family.

Testing a drawer: call `installDrawerTestEnv()` (`drawer/testEnv.ts`, which also turns animations off) and wrap the render in `TestHarness` (`drawer/TestHarness.tsx`: store with a role, query client, Mantine, layout tier); mock the feature's hooks as `ItemDetailDrawer.test.tsx` does. A tab or modal that opens through a transition needs `await vi.waitFor(...)` inside `act`.

## Dashboard KPI cards

`MetricCard`/`MetricCardRow` (`src/shared/components/MetricCard.tsx`) is the reference component for a screen's top-of-page KPI strip — e.g. Sales & Invoices History's Today's Sales/Invoices/Outstanding Credit/Avg Basket Value, or Repair Jobs'/Print Jobs' Today's Jobs/Revenue/Open Tickets/Avg Value. Render a `<MetricCardRow cards={[...]} staleAsOf={...} />` rather than hand-rolling another `Paper`/`Group`/`ThemeIcon`/`Skeleton` block — it already reproduces the established shape (uppercase dimmed label, `xl`/`fw={700}` colored tabular-nums value, light-variant `ThemeIcon`, `Skeleton` while loading) and the `SimpleGrid cols={{ base: 1, sm: 2, md: 4 }}` responsive layout.

## Keyboard shortcuts

`useAppShortcuts` (`src/shared/hooks/useShortcuts.ts`) is the single global keyboard-shortcut engine — bind through it rather than a component-local `window.addEventListener('keydown', ...)`. Pass an array of `{ key, handler, ignoreInput?, preventDefault? }` entries; `key` is a combo string like `"Enter"`, `"F2"`, `"Ctrl+D"`, `"Ctrl+Shift+H"`, or `"?"` (`ctrl` matches both `ctrlKey` and `metaKey`, so one combo covers Windows/Linux Ctrl and Mac Cmd).

Shortcuts are scoped and stack: a call to `useAppShortcuts(shortcuts, isActive)` registers while `isActive` is true, and the most-recently-activated scope sees a keypress first — if it handles the key, scopes registered earlier (e.g. the billing page underneath an open modal) never see it. This is how a modal binds its own `Enter`/`Escape` and have it take priority over the page behind it without either side coordinating — see `A4InvoicePreviewModal`'s `Enter` → print binding, which fires the print handler directly rather than focusing the Print button (don't reintroduce the old pattern of `ref.focus()`-ing a button just to make Enter click it; bind the key instead).

`ignoreInput: true` makes a shortcut fire even while a text `<input>`/`<textarea>`/contenteditable elsewhere has focus (used for things like F-keys and Ctrl-combos that should work globally); omit it for shortcuts that should be suppressed while the user is typing.

Shortcut hint labels baked into component text (`"(F2)"`, `"Hold (Ctrl+H)"`, etc.) and `KeyboardShortcutsModal.tsx`'s shortcut list are hand-maintained, not generated from the registry — a deliberate scope decision, so update both by hand when a binding changes.

## Architecture

**Entry chain**: `index.html` → `src/main.tsx` → `src/app/App.tsx` → `AppProviders` (`src/app/providers.tsx`) wraps `RouterProvider` (`src/app/router.tsx`).

- `src/App.tsx` at the repo root is a one-line re-export of `src/app/App.tsx`, left over from the initial Vite scaffold. Treat `src/app/App.tsx` as the real entry component; don't add logic to the root-level one.
- Routing (`src/app/router.tsx`) is a single `createBrowserRouter` tree: all authenticated routes (`billing`, `repairs`, `print-jobs`, `inventory`, `customers`, `reports`) render inside `AppShell` (`src/app/layout/`), which provides the header/sidebar chrome. `/login` is outside the shell. Unknown paths and `/` redirect to `/billing`.
- `AppProviders` sets up, in order: Redux (`Provider` from `react-redux`, `store` from `src/store/index.ts`), TanStack Query (`QueryClientProvider`, 5 min `staleTime`, refetch-on-focus; changes made on other computers or the website mark queries stale as they happen through `LiveRefresh` in `features/sync-status` — map a new synced record type to its query roots in `lib/resourceQueryKeys.ts`), Mantine (`MantineProvider` with `mantineTheme` from `src/styles/theme.ts`, `mantineCssVariableResolver` from `src/styles/cssVariablesResolver.ts`, and `colorSchemeManager={reduxColorSchemeManager}`), `Notifications`, `ModalsProvider`. Mantine/notifications/dates CSS is imported here — new Mantine subpackages (e.g. carousel, dropzone) need their CSS imported wherever they're first used.
- `src/styles/theme.ts` defines the custom `fontSizes`/`spacing` scales (including non-default tokens like `"2xl"`–`"5xl"` and `"3xs"`–`"3xl"`) and per-component default props (`Container`, `Paper`, `Card`, `Select`, `Tooltip`, `HoverCard`) — prefer these theme tokens over hard-coded pixel values, and extend `components` here rather than passing repeated default props at call sites. `src/styles/cssVariablesResolver.ts` is the place to add custom CSS variables (light/dark/scheme-independent) consumed via `var(--...)`.
- `defaultRadius: 'md'` in `src/styles/theme.ts` sets the app-wide corner radius. **All components should use the default radius** (`var(--mantine-radius-default)`) — prefer omitting the `radius` prop entirely so components inherit it. If a place needs the radius stated explicitly (e.g. a raw CSS `border-radius` outside a `radius` prop), reference `var(--mantine-radius-default)` rather than hard-coding pixels/fixed tokens, so it keeps tracking the theme default. Never pass a smaller explicit `radius="sm"` or override unless specifically required.
- **Interactive Tooltips & HoverCards**: `InteractiveTooltip` (`src/shared/components/InteractiveTooltip.tsx`) is the standard component across the app for interactive or rich tooltips (built on Mantine's `HoverCard` so the mouse can smoothly enter the tooltip without closing). It automatically uses `var(--bg-card)`, `var(--border)`, `var(--text-primary)`, `var(--text-secondary)`, and `var(--mantine-radius-default)` to support light/dark theme switching seamlessly. It supports `title`, `description`/`content`, leading `icon`, `shortcut` key chips ([`Kbd`]), `badge`, and custom `footer` nodes. `ExpandableCard` (`src/shared/components/ExpandableCard.tsx`) natively supports a `tooltip` prop (`string`, `ReactNode`, or `InteractiveTooltipProps`) on its header without interfering with independent action buttons (e.g., used on Existing Categories cards in `CategoryManagerModal.tsx` to indicate sub-categories).

**Feature modules** (`src/features/<name>/`): each feature (`auth`, `billing`, `customers`, `inventory`, `print-jobs`, `repairs`, `reports`) follows the same shape — `components/`, `types.ts`, and an `index.ts` barrel that re-exports the public component(s) and `* from './types'`. Import features only through their barrel (`@/features/billing`), not by reaching into `components/`.

**Path alias**: `@/*` maps to `src/*` (configured in both `tsconfig.json` and `vite.config.ts` via `vite-tsconfig-paths`). Always import with `@/...` rather than relative `../../` paths across module boundaries.

**Cross-cutting layers**:

- `src/api/client.ts` — a single `ApiClient` class (`apiClient` singleton) wrapping `axios`, base URL from `env.apiBaseUrl`, auto-attaches `Bearer` token from `localStorage[STORAGE_KEYS.AUTH_TOKEN]`, normalizes failures into the `ApiError` shape (`src/shared/types/common.ts`).
- `src/api/queryKeys.ts` — centralized TanStack Query key factory, one namespace per feature (`billing`, `repairs`, `printJobs`, `inventory`, `customers`, `reports`). Add new query keys here rather than inlining key arrays in components/hooks.
- `src/constants/` — shared business constants, re-exported through `index.ts`: `payment.ts` (`CURRENCY`, LKR/"Rs.", `PAYMENT_METHODS`), `jobs.ts` (repair job status enum + labels + colors, `JOB_STATUS*`), `routes.ts` (`ROUTES` absolute + `ROUTE_PATHS` relative — a new route needs an entry in **both**), `roles.ts`, `ui.ts` (default pagination), `storage.ts` (`STORAGE_KEYS` — localStorage key names; add new keys here rather than inlining string literals). Note several mock stores still hard-code their keys and bypass `STORAGE_KEYS`; don't copy that.
- `src/config/env.ts` — typed wrapper over `import.meta.env`. Multi-tenant web build (`VITE_MULTI_TENANT=true`): the login asks for a shop code **and a username** (never an email; a shop's owner is always `admin`, and the link may carry `?username=admin`), sets it from a `?shop=<code>` link (the SimpleBash app's "Open POS" button): a valid link hides the field and shows "Signing in to <code> · Not your shop? Change", and a failed login (400/401) or "Change" brings the input back (state in `useLoginShopCode`, `getInitialShopCodeState` in `features/auth/lib/shopCode.ts`); without a link the input stays visible, prefilled from the code remembered in `localStorage['pos_shop_code']` after each successful login (empty on a first visit), and shows a "Create your shop" link to `env.accountsUrl` (`VITE_ACCOUNTS_URL`, default https://app.simplebash.com) for people without a shop.
- `src/shared/` — cross-feature reusable code: `components/` (e.g. `DataTable`, `MoneyInput`, `ConfirmDialog`, `EmptyState`, `PageHeader`, `InteractiveTooltip`, `ExpandableCard`), `lib/` (`money.ts`, `date.ts`, `print.ts`), `types/common.ts` (`PaginatedResponse`, `ApiError`, `ApiResponse`, `SelectOption`).

**State management (Redux Toolkit)**: `src/store/` is the app's single global client-state layer — there is no other state library in this project (no Zustand/Context-based stores). `src/store/index.ts` builds the store via `configureStore` and exports `RootState`/`AppDispatch`; always use the typed `useAppDispatch`/`useAppSelector` from `src/store/hooks.ts` instead of the raw `react-redux` hooks. New client state goes into a new slice under `src/store/slices/`, following `cartSlice.ts`'s pattern: plain field reducers via `createSlice` (Immer draft mutation), with any derived/computed values exposed as memoized selectors (`createSelector`) rather than recomputed inline in components.

- `src/store/slices/cartSlice.ts` — the active billing cart (line items, customer, discount, payment method). Derived totals (`selectSubtotalCents`/`selectTaxCents`/`selectTotalCents`/`selectCartItemsCount`) are selectors, not stored state — don't add `subtotalCents` etc. as actual reducer fields.
- `src/store/slices/themeSlice.ts` + `src/store/colorSchemeManager.ts` — color-scheme (`'light' | 'dark'`) state, with a custom `MantineColorSchemeManager` (`reduxColorSchemeManager`) bridging it to `MantineProvider`, so Redux — not Mantine's default `localStorage` manager — is the single source of truth. Persisted via a `createListenerMiddleware` listener (`src/store/listenerMiddleware.ts`) to `localStorage[STORAGE_KEYS.COLOR_SCHEME]`. `index.html` has an inline `<script>` duplicating the same initial-scheme resolution logic to prevent a flash of the wrong theme on load — if the storage key or fallback logic ever changes, update both `themeSlice.ts`'s `getInitialColorScheme()` and that script together.
- **Design tokens**: `src/styles/cssVariablesResolver.ts` defines the app's neutral palette as scheme-flipping tokens — surfaces (`--bg-app`, `--bg-sidebar`, `--bg-card`, `--bg-hover`, `--bg-active`), borders (`--border`, `--border-strong`), text (`--text-primary`, `--text-secondary`, `--text-muted`), and status (`--status-ok`, `--status-busy`, `--status-warn`, `--status-error`, `--status-idle`, each with a `-bg` pair). Status tokens are named by meaning, not colour. Style with `var(--bg-card)` / `var(--text-muted)` etc.; never a raw hex, so a theme switch is only a value flip. Mantine's semantic vars (`--mantine-color-body`, `-default`, `-default-hover`, `-default-border`, `-text`, `-dimmed`, `-placeholder`) are re-pointed at these tokens in the same file, so built-in Mantine components follow the palette automatically — either name works, prefer the `--bg-*`/`--text-*` tokens in app code.
- **Dark-mode-safe styling**: never use fixed swatch vars (`--mantine-color-gray-0`…`-9`) or raw hex codes for anything that should look right in both themes — swatch vars don't change between light/dark. Both the light and dark values live in `cssVariablesResolver.ts`; define every token in both blocks so a scheme switch is only a value flip. (`theme.ts` defines one custom colour, `amber`, and no `colors.dark` override — Mantine's built-in dark scale applies.)

**No implicit fallbacks — be explicit**: don't paper over a missing value with `||` / `??` defaults, and don't invent a default at the consumption site (`textAlign: col.align || 'left'`, `icon || <IconInbox />`, `getElementById('root') || getElementById('app')` are all the anti-pattern). If a value matters to how something renders or behaves, make the field **required** in the type so every call site states it exactly — `align: 'left' | 'center' | 'right'` on `Column`, not `align?`. If a value is genuinely optional, let it be `undefined` and pass it straight through (e.g. `width: col.width`) rather than substituting a guessed stand-in. The narrow exception is documented environment configuration (`src/config/env.ts`), where a fallback is the declared default for a missing `import.meta.env` var.

**Money handling**: all monetary values are stored and passed around as integer cents (`unitPriceCents`, `totalCents`, etc.), never floats. Use `src/shared/lib/money.ts` (`toCents`, `fromCents`, `formatMoney`, `parseMoneyToCents`) to convert and format — don't do ad hoc float math on currency. **Working money out is not the frontend's job**: see **Live calculations come from the server** below.

**Backend status — fully migrated, direct REST**: every domain is on a real REST backend under `env.apiBaseUrl` (`/api` by default) — inventory (products, categories), suppliers, supplier-products, purchases, customers, billing/invoices, payments, repairs, print-jobs and employees all read/write straight through `apiClient` + TanStack Query, the same way `users`/`auth`/`reports` always have. **Employees** (`src/features/employees/`) is the HR/commission profile domain — a separate, optional login account (`src/features/users/`) can be linked to one via `employeeKey`.

A "fetch everything" hook (`useAllInvoices`, `useAllProducts`, etc.) must not silently truncate at the backend's per-page cap (100–200 items depending on module) once a shop's data outgrows one page — loop pages with `fetchAllPages` (`src/shared/lib/fetchAllPages.ts`) or an inline equivalent (see `fetchAllInvoices`/`fetchAllRepairs`/`fetchAllPrintJobs`/`fetchAllProducts`/`fetchAllCustomers`). A hook backing a debounced backend search (via `useBackendFilteredList`, see below) stays a single capped page — a search wants the top matches, not the whole collection.

An offline-first sync engine (mirroring every resource into IndexedDB, queuing writes in an outbox, reconciling conflicts) used to sit between the UI and this API and has been removed — the app now depends on the backend being reachable, the same as any ordinary web app. **A future, separate sync backend is planned** to bring back cross-terminal syncing; until then, see **Local database** below for what's left in place and **Sync UI (disabled)** for what's parked pending that work.

## Live calculations come from the server

Business maths and rules (landed cost, charge spreading, selling price and margin, totals, discounts, change, validation of "can this be saved") exist **once, in the Rust backend** (`modules/calc` and the engines it calls; see the backend CLAUDE.md). The frontend never re-implements or "double-checks" them, and never falls back to computing locally when the server is slow or down.

- **State holds what was typed; the reply holds everything worked out.** A form maps its state to a request (`toCalcReceiptRequest` in `features/purchases/lib/receiptForm.ts` is the reference) and reads the reply with `useCalc(name, request, fetcher)` (`src/shared/hooks/useCalc.ts`). One request per change, no debounce; the request still in flight is aborted by the next change; the previous answer stays on screen (`isCurrent` is false and the figures are dimmed, in fixed-width spots so nothing shifts) until the new one lands.
- **Save/Pay waits for `isCurrent`** and for an empty `blockers` list; the server's figures (not locally derived ones) are what get sent. If the call fails, show the error and keep Save off. Blockers are codes; `lib/blockerText.ts` maps them to `t()` sentences.
- **Toggles use the reply's counterparts** (e.g. `costAsUnitCents`, `costAsLotCents`, `marginTenthsIfSwitched`): switching Price each/Whole lot or price/margin copies the server's number into the state, it does not compute it.
- **Not-entered values**: a box still empty is `null` in the request, a money box with nothing typed is `0`; a reply figure that cannot be worked out yet is `null`/0 as documented on the backend reply type. Do not invent defaults for them.
- **API client**: URLs under `/calc/` carry no `Idempotency-Key` and do not trigger the desktop's `syncNow()` (`isLiveCalc` in `api/client.ts`). Keep new calculators under `/calc/`.
- **Tests**: script the server's answer with literals (see `ReceiveStockModal.test.tsx`: `answerWith`, `lineReply`); never compute expected figures in a frontend test. The formulas' vectors live in the Rust tests and `tests/golden/calc/*.json`.
- **Billing cart and payment** (`features/billing/hooks/useCheckout.ts`): the cart (`cartSlice`) holds only what was typed: price, quantity, the line discount as typed (`CartItem.discount`: a percentage of the line or fixed cents, so a percentage follows the quantity) and the order discount as typed (`discountType`/`discountValue`). `useCheckout()` sends the whole cart plus its payment inputs to `POST /calc/checkout` and returns the server's lines, subtotal, order discount, total, retail/repairs/print split, payment state (change, short by, split, credit) and quick-tender buttons; `PaymentPanel`, `CartPanel`, `BillingCounter`, `BillingTabBar` and `DiscountPopover` all read from it (one shared answer). `PaymentPanel` is a thin wrapper that shows a waiting/error line until there is an answer, then renders the body from it; the sale is sent with the server's `amountReceivedCents` and each line's `discountCents`/`totalCents`, and only when `isCurrent`. Each request line carries a `key` (the cart line's id) that its answer echoes: **look a row's figures up by that key, never by position**, because the answer on screen may be for an earlier cart. Parked carts get their totals from `useHeldCartTotals`. Parked carts saved before this change are read once as fixed discounts (`toTypedLineDiscount` in `cartSlice`).
- **Returns** (`features/invoices/components/CreditNoteModal.tsx`): the modal holds what the cashier picked (lines and quantities, condition, exchange items, typed refund amounts); `POST /calc/credit-note` answers what each unit is worth back (the line's net total over the units sold, to the cent below, exactly as the credit note is created), the net, the cash refund (capped at what was paid), the default refund legs, and `pastReturnWindow` from the server's `RETURN_WINDOW_DAYS`. A returned line is asked by its position on the invoice; answers come back in the order asked.
- **Quotations** (`features/quotations`): a line holds its discount as typed (`discountType`/`discountScope`/`discountValue`), never in cents. `POST /calc/quotation` answers each line (found by `key` = the line's `uid`), the gross and discount totals, the order discount, the total and `blockers` (mapped to words in `lib/blockerText.ts`). The create request sends each line's `discountCents` from that answer. `LineDiscountPopover` previews the typed discount through the same endpoint while it is open.
- **Cash** (`features/billing/components/sessions`): the cash form sends `toCalcRequest(form, ...)` to `POST /calc/cash-movement` and reads the drawer figures, `pinRequired`, `overDrawer` and `blockers` (words in `movement/blockerText.ts`) from the reply; the PIN and reason text are never sent, only whether they were entered. `DenominationCounter` only holds the typed counts: the total and each subtotal come from `POST /calc/cash-count` (`hooks/useCashCount`, called by the parent so it can use the total), and the same hook adds up a saved count in the shift drawer. Open and close use `POST /calc/shift-count`: at close, once the count is recorded, the variance, reason/PIN need, closing float and safe deposit all come from it (a float is `null` until chosen and the server suggests the opening float); a shift's expected cash is always `session.expectedCashCents` from the server.
- **Repair and print job earnings** (`shared/hooks/useJobEarnings.ts`): `toEarningsRequest(form.values)` turns the rupee boxes into cents, `POST /calc/earnings` answers profit, commission, `capped` and what the shop keeps; used by `RepairFormModal`, `PrintJobFormModal` and the employee screen's sample job. A fixed commission is never more than the profit.
- **Supplier payments against bills** (`purchases/hooks/useSettlement.ts`): `POST /calc/settlement` answers what is owed, the oldest-first spread, the "pay everything" split and blockers (words in `lib/settlement.ts`); `SettlementPicker`, `PaySupplierModal` and the supplier drawer read it.
- **Invoice balance** (`billing/hooks/useInvoiceBalance.ts`): `InvoiceDetailDrawer` reads what is owed from `POST /calc/invoice-balance`; the mutations that change payments or returns call `invalidateInvoiceBalance` (a calc answer is cached by its request, so anything that changes the data behind a request must invalidate its `['calc', name]` key). The credit deposit input limit is the checkout reply's `maxCreditDepositCents`.
- **Dashboard**: today's sales, invoice count and average basket come from the billing stats endpoint, the cash widgets from the open shift (`useCurrentSession`), and everything else (pipelines and their shares, technician load, fast movers, low stock, repairs waiting for pickup and their value, the activity stream) from `GET /reports/dashboard-pulse`. `toDashboardData` only words and colours the server's answer.
- **Bars and shares** (`shared/hooks/useShares.ts`): progress and split bars (shift payment mix, regular-bill progress) take their percent from `POST /calc/shares`; the expense report sends `sharePercent` and the chart bands (`chart`, with the "other" band already added up). Never divide cents in a component.
- **Shift list totals** (`billing/hooks/useShiftTotals.ts`): the Register Shifts KPI cards come from `POST /calc/shift-totals` over the keys of the shifts the list is showing (the list's own filters stay on the screen).
- **Sale confirmation** (`saleHeroPresentation.ts`): a sale on account shows the paid and owed figures from `useInvoiceBalance`; until they arrive there is no confirmation card (`getSaleHeroPresentation` returns `null`).
- **Settlement picker**: ticking a bill puts in the server's `ifTicked` amount.
- Counts for badges (lines in the cart, units) are the one thing computed locally (`selectCartItemsCount`, `selectTotalUnitCount`): they are counts, not money.
- What stays in the frontend: formatting (`formatMoney`), parsing typed text to cents, choice lists such as `lib/priceSteps.ts`, and UI-only state.

## Local database

`src/offline/` is what remains of the removed sync engine — kept as infrastructure for a possible future non-sync local-storage feature, not because anything currently depends on it for correctness:

- `src/offline/db/schema.ts` — the `OfflineDb` Dexie class and `db` singleton. Only real table today: `statsCache` (`db/tables.ts`'s `StatsCacheRow`) — see **Dashboard KPI cards** above. Bump the Dexie version for any schema change; never edit an installed `this.version(n)` block in place, or it bricks the app for anyone who already has data at the old version.
- `src/offline/db/maintenance.ts` — `estimateStorage`/`requestPersistentStorage`, generic browser storage-quota helpers, unrelated to any specific table.
- `src/offline/connectivity/` — `ConnectivityMonitor` combines `navigator.onLine`, the `statusCode: 0` signal from the `apiClient` response interceptor, and a `GET /health` probe into one verdict, with asymmetric hysteresis (offline publishes immediately, online is held for a settle window). Its only consumer is `onlineManagerBridge.ts`, wired in `providers.tsx`, which feeds TanStack Query's `onlineManager` so background refetches correctly pause/resume with real connectivity — `navigator.onLine` alone only sees the link layer (a terminal on a router with no upstream still reports `true`). Never call `navigator.onLine` directly in a component.
- `src/offline/react/useLiveQuery.ts` — a generic Dexie `liveQuery` → React state hook, used by `useModuleStats` to read `statsCache`.

Auth is strict online-only (`authSlice.ts`'s `initializeAuth`): any failure to verify the stored token — 401/403, a network error, a 500 — signs the user out. There is no cached-session offline grace period.

## Sync screen (desktop, live)

`src/features/sync-status/` is the live sync UI (not `features/sync/`, which is the parked dead code above). The shell's `sync://status` payload carries `step`, `progress`, per-record-type `modules`, `lastCycle`, `nextRetryAt` and a 20-line `history`; `sync_list_pending` lists the individual waiting changes with readable names (backend `GET /api/sync/outbox/pending`).

- All wording and state-to-view mapping is pure and tested in `lib/syncView.ts` (`heroView`, `moduleRows`, `activityView`) and `lib/statusView.ts` (`badgeView`). Sentences are arrays of static phrases plus numbers (`Phrase`) so each static phrase goes through `t()`; render them with `phraseText`. Add new phrases to `si.json`.
- `MODULES` in `syncView.ts` maps backend record types to shop words (Sales & Invoices, Repair Jobs…). A new syncable resource in the backend's `SYNC_RESOURCES` needs a line there or it shows under "Other records".
- **Per-module chips follow the data.** Each row in "What's syncing" is decided by `moduleRows()` from that row's own numbers, which the shell fills as the cycle runs (`pending`, `sent`, `received`, `lastChange`; see `ModuleStatus` in `src-tauri/src/sync/state.rs`): Sending x / y, Receiving N, Waiting N, Needs review N, a green "Sent N · Received M" for 30 s after a row finishes, then Up to date with "Updated hh:mm". ## Suspended shop page (web)

When SimpleBash suspends a shop's owner account, every cloud request of that shop (and a shop-code login after the password check) answers `403 ACCOUNT_SUSPENDED` with `details {shopName, suspendedAt, reason, retained {bills, products, customers, staff, lastBillAt}}`. `api/client.ts` passes each failed response to `notifyIfSuspended` (`features/account/lib/suspension.ts`; skipped on the desktop, whose shell pauses sync itself), which — only for a complete, well-typed answer (`parseSuspension`, no defaults) — calls the handler registered in `app/App.tsx`: it saves the suspension to `sessionStorage` and navigates to `ROUTES.SUSPENDED`. `AccountSuspendedPage` (outside `RequireAuth`/`GuestOnly`) shows the reason, the retained data counts ("Your data is safe"), what is paused vs still working, and the contact from `VITE_SUPPORT_EMAIL` / `VITE_SUPPORT_WHATSAPP` (required: `env.supportEmail` throws if unset; wired through the Dockerfile, CI and `pos/deployment/scripts/deploy.sh`). With nothing stored it redirects to the sign-in page. Tests: `features/account/__tests__/suspension.test.tsx`.

## Desktop activity log

The desktop app records everything that happens into a unified, append-only log written by the Tauri shell (`<app data>/logs/<day>/<source>.jsonl`, schema in the pos-compose repo's `docs/logging.md`). The frontend side lives in `src/shared/logging/` and is a no-op in the browser.

- **Automatic capture** (installed once by `initLogging()` in `src/main.tsx`): clicks/double/right clicks, debounced typing (final value), committed changes, form submits and named/modifier key presses (`capture/dom.ts`); route changes (`capture/navigation.ts`); every `apiClient` and health-probe call with an `X-Request-Id` the backend and document-server log under too (`capture/http.ts`); every Redux action and the signed-in user (`capture/state.ts`); TanStack query failures and mutation lifecycle (`capture/query.ts`); uncaught errors, unhandled rejections and React root errors (`capture/errors.ts`); the console (`capture/console.ts`); visibility, online/offline, resizes, long tasks, Mantine notifications and modals (`capture/app.ts`).
- **Explicit events**: call `logger.event(category, event, data)` (or `logger.info`/`warn`/`error`) from `@/shared/logging` for business or workflow steps automatic capture can't name (see `UpdatesSection.tsx`, `printService.tsx`, `WelcomeWizard.tsx`). Add a new category to `LogCategory` in `src/shared/logging/types.ts`.
- **Label critical controls** with `data-log-id="<feature>.<action>"` (e.g. `billing.complete-sale`) so their log label survives copy and language changes.
- **Sensitive fields**: passwords, `autocomplete="cc-*"`/one-time codes and any key matching the shared secret pattern are redacted automatically; mark anything else that must never be logged with `data-log-redact` (on the field or a container).
- **Cost**: captured payloads must go through `redactAndCap` (`shared/logging/redact.ts`) — a single budgeted walk that stops at the cap. Never `JSON.stringify` a whole API body to measure or cut it; that made a 6 MB list cost ~32 ms instead of ~0.2 ms. `logger.pause()`/`resume()` and `logger.stats()` exist for the benchmark below.
- **Benchmark**: Settings → System Benchmark has a `logging` phase (`settings/lib/loggingBenchmark.ts`) that replays a simulated, read-only sale flow with logging off/standard/full and reports CPU, memory and disk per 1,000 sales via the shell's `benchmark_log_mode` / `benchmark_resource_sample` commands. It restores the user's saved logging settings in a `finally`. Re-run it (or `npm run bench:logging` in the pos-compose repo) after changing anything in `shared/logging/`.
- **Viewer**: Settings → Activity Log (`src/features/logs/`, section `LogsSection.tsx`, desktop-only + admin-only) — filters, live tail, "Trace this request", open folder, ZIP export and logging options.

## API client conventions

`src/api/client.ts`'s `apiClient` auto-attaches an `Idempotency-Key` header (a fresh UUID per request, via `createIdempotencyKey()` in `src/shared/lib/id.ts`) to every mutating request (POST/PUT/PATCH/DELETE) in its request interceptor — this is what makes retrying a request whose response was lost (a power cut mid-request) safe; the backend returns the original response instead of double-applying the write (`Idempotency-Key`, stored key → response for 7 days — see the backend CLAUDE.md). Callers never need to set this themselves. There is no client-side optimistic-concurrency (`If-Match`) support — a version conflict on a genuinely concurrent edit is last-write-wins; the backend still supports `If-Match` for any caller that wants to send it, but nothing in this frontend does today.

`POST /sequences/{name}/reserve` mints sequential human-facing numbers (`INV-2026-0042`, `REP-…`, `PRT-…`) server-side at the moment a sale/repair/print-job is created — never client-side, never a localStorage counter or array-length-derived number.

## Cash movements (`src/features/billing/components/sessions/`)

`CashMovementModal` records every drawer cash event as one of eight kinds (`CashMovementType`: `petty_expense`, `rent_and_bills`, `staff_payment`, `supplier_payment`, `owner_withdrawal`, `add_cash`, `cash_drop`, `no_sale`); the server derives the direction. There is no free-text reason: every movement is filed under a **category** (data the shop grows, `GET/POST /cash-categories`) and, where the kind needs one, a payee. The helper line "Enter amount to add or withdraw" is gone on purpose; the kind already decides the direction.

- **Files** (`sessions/movement/`): `movementTypes.tsx` (groups, labels, hints, the sets `MANAGED_TYPES` / `ALWAYS_PIN_TYPES` / `CASHIER_CATEGORY_TYPES` that mirror the server's rules; labels are functions so `t()` runs at render), `movementForm.ts` (pure state: `emptyForm`, `switchType`, `toCalcRequest`, `toInput`, `periodRange`; no React, tested alone; the rules are the server's), `MovementTypePicker` (a direction tab strip with a gliding `layoutId` pill, then one `ChoiceCard` per kind with icon, name and what it is for; on a phone only the chosen card shows its line; keys 1 to 8 still pick a kind on a computer and the cards say so in a tooltip, there are no number badges), `CategoryPicker` (the five most used categories as `ChoiceCard`s ranked by the server's `usageCount`, a dashed **More** opens the searchable list, a pinned footer adds a category inline), `MovementDetailFields` (the fields of each kind, with the labels that make sense for it), `ChoiceCard`/`ChoiceGroup` (the one "choose one" look: `role=radiogroup`/`radio`, arrow keys move and choose, outline when not chosen, blue border + tint + a tick that pops in when chosen, `.choice-card` in `global.css`), `MovementStep` (numbered step heading: 1 What happened? 2 How much? 3 what it is for, 4 Details; the amount step is left out for a no-sale open) and `ShortcutPills` (tinted pills that fill the field above, e.g. quick amounts and "Drop excess"). **Visual language**: a choice is a radio card, a shortcut is a tinted pill with a grey caption, a field is a bordered input, information (the drawer balance) is plain text with an icon and never a grey bar that looks like an input. Motion: the kind-specific steps fade in as one piece when the kind changes (`FadeIn` keyed by kind), the PIN block, over-drawer warning and errors fade in and out (`AnimatePresence`), the drawer figures count with `AnimatedNumber`; opacity and transform only. The modal follows the **Center modals** family: plain title, `centered`, `fullScreen={isMobile}`, Cancel `variant="default"` + blue primary, no per-kind colours.
- **`SearchCombobox`** (`shared/components/`) is the one searchable list for every "pick one or add a new one" field (category, supplier, vendor, staff, payee, later bank account). Search ignores case and spacing (`shared/lib/compactText.ts`) and also matches `searchText` (the Sinhala name); the create footer is pinned under the list, Enter on a typed name that matches nothing creates it. Pass `create` when the person may add entries and `noCreateHint` ("ask a manager") when they may not; `emptyText` is required (no hidden default). Not the catalogue's `lib/search.ts` engine.
- **Add / failed notifications live in one place** (`src/api/mutationFeedback.ts`): a mutation hook that adds something declares `meta: feedbackMeta<Result>({ successTitle, successMessage, failureTitle })` and every screen using it shows the same green or red notification (`attachMutationFeedback` is attached to the query client in `app/providers.tsx`). This works for any mutation anywhere in the app, not only dropdowns. A screen never writes its own add/fail toast for a hook that declares it (that would show twice); it keeps only the inline field error. Today `useCreateCashCategory` and `useCreatePayee` declare it. Tests: `api/__tests__/mutationFeedback.test.ts`, `billing/hooks/__tests__/useCashLookups.feedback.test.tsx`.
- **Inline category creation**: a new name is confirmed in place (editable name, "did you mean" matches from `GET /cash-categories/similar`, "Save for future use" ticked by default). Unticked, the movement is filed under the kind's **Other** with the name as `customLabel` (not offered when a kind has no Other, i.e. cash drop). A cashier can add only to `CASHIER_CATEGORY_TYPES`; anything else shows the ask-a-manager hint. New categories carry a "New" badge until a manager reviews them.
- **Permissions** (`constants/permissions.ts`, mirroring the server): `cash_movements:create:managed` unlocks rent and bills, staff payment and supplier payment (the chips are greyed with a tooltip without it); `cash_categories:create` / `cash_categories:manage`; `payees:manage`; `suppliers:create` (register a supplier from the supplier payment list; Admin and Manager, granted at the next sign-in). A manager or owner PIN is needed for owner withdrawals, staff payments and any amount above a category's `requiresApprovalOverCents`; the old fixed Rs. 500 admin limit no longer exists.
- Query keys: `queryKeys.billing.cash.*`; `cashMovements`, `cashCategories` and `payees` are mapped in `sync-status/lib/resourceQueryKeys.ts` so another device's change refreshes the pickers. The shift drawer's movement table shows a direction badge (`getDirectionLook`), the category, the payee and the note. `sessionPrint.ts` escapes everything typed before it goes into the voucher HTML.
- **Drawer safety**: under the amount the modal shows "In the drawer now" and, once an amount is typed, "In the drawer: Rs. A → Rs. B", using the server's `POST /calc/cash-movement` answer; nothing is previewed or blocked until it has loaded. A payout bigger than the drawer holds (`overDrawer`) shows a warning, asks for a manager or owner PIN **and** a reason (`overrideReason`), and is otherwise blocked. After saving, the success card offers **Undo this entry** while `undoUntil` (from the server) is in the future (`useUndoWindow` turns it off by itself). The shift drawer's movement table marks a reversed entry (struck through, "Reversed") and its reversal ("Reversal", with the reason), nets reversals out of the totals (`signedAmount`), and gives people with `cash_movements:reverse` a **Reverse entry** action (`ReverseMovementModal`, a reason is always asked) while the shift is open. The table sits in `Table.ScrollContainer` so extra columns scroll instead of clipping.
- **Inline landlord/company creation** (`movement/PayeePicker.tsx`, rent and bills only): anyone with `payees:manage` gets the pinned "+ Add" footer; it opens a small form (name 2 to 60 letters via `billing/lib/payeeName.ts`, mirroring the server's `clean_name`, plus an optional phone), saves a `vendor` payee through `useCreatePayee` and picks it. Others see the ask-a-manager hint. "Same as last time" is not offered when that payee has since been hidden (the server refuses hidden payees on new payments with `PAYEE_HIDDEN`). Pickers never ask for hidden payees; only Settings sends `includeHidden`.
- **Registering a supplier from the form** (`movement/SupplierPicker.tsx`, supplier payment only): anyone with `suppliers:create` (Admin and Manager) gets the pinned "+ Add" footer; it opens the same **Register New Supplier** window as the Suppliers page (`SupplierFormModal` with `linkProducts={false}`, so no product links: those endpoints are Admin-only; `initialName` is the name typed in the list). `useCreateSupplier` returns the invalidation of the supplier lists **and** `queryKeys.billing.cash.all`, so `mutateAsync` resolves once the payee list holds the new supplier; the picker then selects its `sup_...` key and shows the "Supplier Created" notification. A failed save keeps the window open with its inline error and picks nothing. **Escape:** every open Mantine modal closes on Escape (a window-level capture listener, so stopping React propagation does nothing), so the picker reports its window opening and closing (`onWindowOpenChange`, through `MovementDetailFields` as `onNestedWindowChange`) and `CashMovementModal` sets `closeOnEscape={!nestedWindowOpen}`; any future window opened from inside the cash window must do the same. Everyone else sees "To add a supplier, ask a manager.". Only the create route accepts `suppliers:create`; list, edit and delete stay Admin-only. Tests: `movement/__tests__/SupplierPicker.test.tsx`, `suppliers/hooks/__tests__/useSuppliers.test.tsx`, `SupplierFormModal.test.tsx`, the supplier cases in `CashMovementModal.test.tsx`.
- Not built yet (later phases): slide-overs to add a staff member or bank account from the form, remembered last kind per cashier, the cash-drop "drop excess" helper.

## Expenses (`src/features/expenses/`)

The Expenses page (`ROUTES.EXPENSES`, behind `RequirePermission` `expenses:view`, sidebar item under Sales & Operations) lists every business cost newest first: payments taken from the cash drawer (read from the cash movements by the server, shown as "Cash drawer", never entered here) together with costs paid from the bank, a card or online and the bills still to pay. KPI strip from `GET /expenses/stats` through `useExpenseStats` (`useModuleStats('expenses', …)`, so the last answer stays available offline); search, "Still owed / Overdue / Paid" and "Cash drawer / Bank, card or online" filters and paging all run on the server. Adding and paying need `expenses:manage` (Manager and Admin).

- `lib/expenseForm.ts` (pure, tested alone: `validateExpense`, `toExpenseInput`, `validatePayment`, `toPaymentInput`, `isDay`) holds the forms' state and plain-language rules; `lib/expenseView.ts` the labels and status chip (overdue wins over "not paid") and `canPay` (only a ledger row with a balance). Neither form defaults how a bill was paid: "How was it paid?" starts unchosen and the person must pick Bank, Card, Online or Not paid yet.
- `ExpenseFormModal` follows the **Center modals** family and reuses `SearchCombobox` for the category (only categories that count as a cost: `useCashCategories({forExpenses: true})`, with the kind of payment shown under each name because several kinds have an "Other") and the payee (a typed name is kept on losing focus and saved to the payee list). `ExpensePaymentModal` shows what is owed and what was paid so far and refuses more than is owed.
- Drawer payments are made on the Cash Movement window; there is deliberately no way to enter drawer cash here. Bank-paid rent and other bank costs are entered here and never change the drawer.
- Query keys `queryKeys.expenses.*`; `expenses`, `expensePayments` and `cashMovements` are mapped in `sync-status/lib/resourceQueryKeys.ts`. Already signed-in people get the new permissions at their next sign-in (permissions travel in the sign-in token).
- **Regular bills** (monthly rent, electricity...): the page has two tabs (`AnimatedTabs`), "All expenses" and "Regular bills" (with a count of bills that are due or overdue). `RegularBillsPanel` lists each bill with status chip, "Rs. X of Y paid", a progress bar and a Pay button (Edit / Stop-Restart too, with `expenses:manage`); `RecurringFormModal` adds or changes one (`lib/recurringForm.ts` holds its pure rules; rent paid from the drawer needs a payee). Paying opens a form already filled in from the bill: a drawer bill opens `CashMovementModal` with its `prefill` prop (needs this register's open shift, otherwise a "Open a shift first" message), any other bill opens `ExpenseFormModal` with its `prefill` (dated on the due day when the bill is for an earlier month). `BillReminderNotifier` (mounted in `app/providers.tsx`, only for `expenses:view`) polls `useRecurringBills` every 10 minutes and puts one bell entry per bill, month and state (`bill-<key>-<period>-<status>`, so a bill that turns overdue reminds again) whose link is `/expenses?pay=<key>`; the page starts that payment (done while rendering, then the query string is tidied). The cash form's rent section asks `usePeriodStatus` (in `billing/hooks/useCashLookups.ts`) once category and month are known and shows "This month is already paid" with a "This is another payment" checkbox (`confirmDuplicate`); it also offers "Same as last time" (payee and amount of the last rent payment) as a tap, never filling silently. Recording or reversing a cash movement invalidates `queryKeys.expenses.all` so the bills refresh at once. The "already paid" check is the cash-movement reply's `periodAlreadyPaid` / `period_already_paid` blocker.
- Tests: `lib/__tests__/expenseForm.test.ts`, `lib/__tests__/recurringForm.test.ts`, `components/__tests__/expenses.test.tsx` (page, add and pay windows, regular bills), `components/__tests__/BillReminderNotifier.test.tsx`.

## Supplier bills (`src/features/purchases/`)

Stock is received as a **bill** (a receipt: one supplier invoice, the header of its product lines). `ReceiveStockModal` is the only way in, opened from the supplier's **Bills** tab, the item's **Stock received** tab and the inventory screens; there are no inline quick forms any more (`SupplierIntakePanel` / `ItemIntakePanel` only list and open the window). The window follows the **Center modals** family: supplier, supplier's invoice number and day, then one `ReceiptLineCard` per product (product, how many, cost of each, selling price each, serial numbers for a serialized item; a product can be on the bill once), then `ReceiptPaymentSection`: _On credit / Paid in full / Part paid_ and, for money paid now, where it comes from (_Cash drawer, My own pocket, Bank, Card, Online_, `ChoiceCard`s; nothing is pre-picked), what it is filed under (the "Stock purchase (cash on delivery)" category is offered first), the day for bank/card/online, and a summary (_Bill total · Paying now · Left to pay later_). The payment is part of the same save as the stock: nothing is sent twice and a refused payment saves no stock. Pure rules live in `lib/receiptForm.ts` (state, totals, `validateReceipt`, `toReceiptInput`; tested alone). A server answer is turned into something the person can act on: `DUPLICATE_RECEIPT` shows "This bill may already be recorded" with _Change the invoice number_ / _This is a different bill. Record it._ (resends with `confirmDuplicate`), and `DRAWER_CASH_EXCEEDED` / `PIN_NOT_SET` / `INVALID_PIN` reveal the manager PIN and reason fields.

- **Paying later**: `PaySupplierModal` (supplier drawer footer **Pay Supplier**, the bills tab, Balances **Pay**) records a payment from the drawer (a `supplier_payment` cash movement) or the bank, a card or online (a ledger expense) and says which bills it pays through `SettlementPicker` (open bills oldest first, a checkbox and an amount for each, "Pay the oldest bills first", "Pay everything owed"); `lib/settlement.ts` / `lib/payForm.ts` hold the pure rules (`autoAllocate`, `validateSettlements`, `validatePay`, the two request bodies). The cash form's **Supplier payment** shows the same picker once a supplier is chosen (`MovementFormState.settlements`). A payment with no bills ticked still lowers what the supplier is owed but leaves every bill unpaid, and the picker says so.
- **Credit**: `RecordCreditModal` (bills tab) records what a supplier took off for fewer/damaged/wrong-price goods, against a bill or the supplier's account; it moves no stock.
- **Lot prices, margin and extra charges**: a product is priced _Price each_ or _Whole lot_ (`SegmentedToggle` in `ReceiptLineCard`; `CostEntry` in `lib/receiptForm.ts`, and the lot total is what is sent as `lineTotalCents`). Price each to lot is exact; lot to price each only when it divides evenly, otherwise the toggle's _Price each_ is disabled with a reason (no rounding of a supplier's price). `LineMarginCard` shows cost each (with the extra charges when there are any), profit each, margin (profit as a share of the selling price, worked out by the server from the lot's landed total) and profit if all sell, red below cost, all read-only. The selling price is set **one way at a time** per product (`SellingPriceFields`, `LineState.pricing`): _I set the price_ (typed; the margin card shows what it earns) or _I set the margin_ (margin wanted + _Round the price up to_ Rs 1/10/50/100; the price field turns read-only and shows the price the server worked out from the landed cost, never stored, so it follows quantity, lot price and charges; switching keeps the price steady using the reply's `marginTenthsIfSwitched`/`sellingPriceCents`; _Don't round_ is a step of 1 cent, and when rounding up moved the price the field says so (`priceRoundedUp`, `priceWithoutRoundingCents`) and the margin card reads _Margin you get_). `ExtraChargesSection` / `ChargeCard`: kind (shipping, customs, handling, insurance, other, supplier discount; `lib/chargeKinds.ts` holds the words, shared with the bill row), an optional _What is it?_ for an _Other charge_ only (dropped when the kind changes, at most 80 letters), amount (always positive; a discount is its own kind), _Who asks for this money_ (_On the supplier's bill_ adds to what is owed; _I pay someone else_ can name an optional `ChargePayeeField` and is paid now from a source chosen once for all such charges), and with two or more products _Spread over the products_ (_By value_/_By quantity_, nothing pre-picked). The spread and rounding are the server's alone (`purchases/charges.rs`, `purchases/pricing.rs`, called through `POST /calc/receipt`); the summary (`ReceiptSummaryPanel`, from the reply's `summary`) shows Goods, the supplier's charges, Bill total, Paying now, Left to pay later and, when a courier is paid, Paid to others and Money going out today. One manager `approval` (`ApprovalFields`, shown after the server asks, only when cash is involved) covers the goods payment and the courier payments together. The server costs the stock (`landedTotalCents`, `landedUnitCostCents`, `chargesShareCents` on each line); the screens only show those.
- Bill state is worded and coloured in `lib/receiptView.ts` (a coloured dot and a word, never a badge: _Not paid, Part paid, Paid_). Amounts owed come from the server (`dueCents`, `GET /purchase-receipts?open=true`); the screens only add up the server's figures.
- Query keys `queryKeys.receipts.*` / `supplierCredits.*`; `purchaseReceipts`, `receiptSettlements`, `supplierCredits` are mapped in `sync-status/lib/resourceQueryKeys.ts`, and recording a bill, a supplier payment, an expense or a reversal invalidates the receipts and balances. Tests: `lib/__tests__/*`, `components/__tests__/ReceiveStockModal.test.tsx`, `components/__tests__/paySupplier.test.tsx`, the supplier and item drawer tests.

## Receipt photos (`src/features/attachments/`)

`ReceiptsAction` is a row button (receipt icon) that opens `ReceiptPhotosModal` for one record; it is mounted on the Expenses rows (a drawer row is a `cash_movement`, a ledger row an `expense`), the Income rows and the shift's Movements table. It is hidden without `attachments:view`; "Add photo" needs `attachments:create` **and** the permission to record that kind of record (`lib/ownerAccess.ts`: `cash_movements:create`, `expenses:manage`, `income:manage`), matching the server. A photo is shrunk in the browser first (`lib/shrinkImage.ts`: longest side 1600 px, JPEG quality lowered until it is under the 900 KB the server's 1 MB limit leaves room for) and sent as base64 JSON; the file input uses `capture="environment"` so a phone opens the camera. Images are fetched with the sign-in token (`GET /attachments/{key}/content` as a blob, `useAttachmentImage`, kept for the session), never an `<img src>` of the API. Up to 5 photos per record. There is no offline upload queue in the web app: on the desktop app the local backend takes the photo while offline and sync carries it later. Tests: `lib/__tests__/shrinkImage.test.ts`, `components/__tests__/receipts.test.tsx`.

## Cash settings sections (`src/features/settings/`)

Two sections of the Settings page (both Admin-only; see _Who may open Settings_ below). **Cash Drawer Rules** (`CashRulesSection`, `lib/cashRulesForm.ts`): the undo window in seconds (10 to 3600), the shop-wide "Manager approval above" amount, the float target and the quick amounts (up to 8, smallest first); an amount left empty clears that rule; saved as one set through `PUT /cash-settings` (`useCashSettings`/`useUpdateCashSettings` in `billing/hooks/useCashLookups.ts`, query key `queryKeys.billing.cash.settings()`), and the form is keyed by the saved `version` so it restarts from what is stored. **Cash Categories** (`CashCategoriesSection`, `CategoryEditModal`, `MergeCategoryModal`, `lib/categoryAdmin.ts`): every category with `includeHidden`, grouped by kind in picker order, with search, a kind filter, "Show hidden" and "Needs review (n)"; each action saves at once (`SectionShell` `hideActions`): approve a cashier-made category, move up/down (swaps `sortOrder` with the neighbour), pin, edit (name, Sinhala name, "Counted in reports as", receipt reminder, per-category approval limit; only changed fields are sent), hide/show, and merge into another category of the same kind (built-in categories cannot be merged, like the server). X)" when the drawer holds more than the float target. ## Money reports (`src/features/finance-reports/`)

## Label printing (`src/features/labels/`)

Barcode/QR stickers for inventory items, printed on label printers. A **label design** is JSON layout data (size in mm plus absolutely placed `text` / `barcode` / `qr` / `line` items, every field required) stored per shop by the backend (`/api/labels/*`, not synced) and drawn by document-server's one parametric Typst template; the frontend never generates Typst. `types.ts` mirrors the backend/document-server contract exactly.

- **Who prints**: Admin and Manager only (`inventory:write`, same as the backend's `/labels/render`, `/labels/jobs`, `/labels/coverage`). The `/labels` route sits behind `RequirePermission`, the sidebar item ("Labels", under Inventory & Supply) has `requiredPermissions`, and `ProductTable`'s bulk "Print Labels (N)" and `ItemDetailDrawer`'s "Print Label" (`onPrintLabel: … | null`) are hidden without it.
- **Labels page** (`LabelsPage`, route `ROUTES.LABELS`): `AnimatedTabs` with **Print** (`LabelPrintTab`: a "Last print · Print again" card + the workspace; its rows live in the page so a half-built print survives a tab switch), **Needs labels** (`LabelCoverageTab`: `GET /labels/coverage` filtered never / new stock / labelled, search, multi-select across pages → rows via `rowFromCoverage`: all the stock of a never-labelled item, only the new units of one that needs labels), **History** (`LabelHistoryTab`: `GET /labels/jobs`, all / printed / saved as PDF, a narrow `RichDrawer` with what was printed, how and by whom, and "Print again"), **Designs** (`LabelDesignsTab`: gallery of to-scale `LabelCanvas` thumbnails, made inert; new / copy / edit / delete). Settings → Label Printing (`LabelsSection`) keeps only this computer's setup and links to the page.
- **Print workspace** (`LabelPrintWorkspace`, controlled `rows`): used by the page and by the thin `LabelPrintModal` (`rows: LabelRow[]`, opened from inventory and from the new-stock offer). Search to add items (`fetchProducts`, the server's matches are not filtered again), remove rows, bulk "1 each" / "Match stock" (`stockCopies`: the stock at the chosen price, 1–500) / "Set all", the price tier (default: the tier a sale draws first, `defaultPriceCents`), and for serial products a unit picker that **starts with every unit in stock chosen** (`serialNumbers: null` until loaded) and drops sold ones on a reprint. "Use this design" appears when an out-of-stock item has no price but the design prints one (`priceFreeAlternative`). "Print a test label" prints the design's sample through `/labels/preview` (not recorded). Enter prints on a computer. `printBlockers()` is the single list of reasons a print cannot go ahead (limits match the backend: 200 items, 500 labels). The preview is `/labels/render` (one of each of the first 12 stickers, never recorded).
- **Print history**: a real print or download goes through `createLabelJob` (`POST /labels/jobs`, built by `jobRequest`: a download names no method/printer/dpi), which answers the PDF and the job key in the `X-Label-Job-Key` header (`apiClient.postWithHeaders`). After `printLabelPdf` the workspace reports `sent`, or `failed` with the reason (≤500 chars); a lost report only leaves the job "No answer from the printer". `usePrintAgain` rebuilds a past job with today's details through `GET /labels/coverage?productKeys=` (`rowsFromJob`; gone products are left out and counted). History is per install (not synced).
- **New stock offers labels**: every stock intake (`useCreatePurchase` in `features/purchases`, so the Receive Stock window, the supplier's and the item's intake forms alike; `labelOfferFor`) and a product created with opening stock (`ProductTable`) call `offerLabelPrint({productKey, copies, priceCents, serialNumbers})` (`lib/labelPrintOffer.ts`, `null` = match stock / default price / every unit). The one listener is `LabelPrintOfferHost`, lazily mounted in `AppShell`; for people who may print it re-reads the product, asks "Print labels for the new stock?" and opens `LabelPrintModal`.
- **Designer** (`LabelDesignerModal`, `LabelCanvas`, `LabelElementEditor`): create / edit / copy a design from the Labels page's Designs tab. Items drag and resize on a to-scale canvas (snap 0.5 mm, pulled onto the label's centre lines within 1 mm with dashed guides, arrow keys nudge, Delete removes); the selected item can be lined up on an edge or centre, copied (Ctrl+D) and moved forward/back in the drawing order; undo/redo (Ctrl+Z / Ctrl+Y) steps through size and items, one drag being one step (`lib/designHistory.ts`, pure); zoom 50–300%. The Preview tab is the server's `/labels/preview`. Starters (`builtIn`) are read-only, copy them to change. `lib/labelGeometry.ts` keeps items inside the label; `designProblem()` mirrors the server's rules, the server has the final say. The sheet is always white with black ink in both themes (it stands for the paper).
- **How it prints** is per computer: `settings.labelPrint: LabelPrintSettings | null` (design, method `system` | `direct`, printer, dpi 203/300/600), persisted with the other settings and **`null` until the person sets it up** (first print opens the setup panel; nothing is defaulted). `LabelPrintSetupFields` is shared by the print window and `LabelsSection`. `direct` (desktop only, `isTauri()`) calls the shell's `list_printers` / `print_label_pages` via `shared/print/nativePrinters.ts`; a failure throws so the person sees it.
- **Print quality**: `printLabelPdf` (`shared/print/printService.tsx`) rasterises at the printer's dpi as lossless PNG thresholded to pure black/white and prints with `image-rendering: pixelated` and the PDF's own page size; documents keep their JPEG 200 dpi path (`DOCUMENT_RASTER`). Never print labels through the document path: resampling blurs thin bars.
- **Billing scan**: `CatalogPanel.handleScanSubmit` tries a scanned code as a serial number last (`inventory/lib/serialScan.ts` → `GET /inventory/serials/by-number/{n}`), adding that exact unit at its own batch's price; the lookup uses the text as typed (the scan term itself is lowercased). A sold unit says so instead of failing silently.
- Errors: requests with `responseType: 'blob'` get their JSON error body read back (`shared/lib/errorBody.ts`, used by the `apiClient` response interceptor), so the server's plain-language reason (barcode too narrow, no barcode yet…) reaches the person.

## Spreadsheet Data Import Engine

`src/features/imports/` provides a reusable, cross-module batch ingestion feature for Excel (`.xlsx`/`.xls`) and `.csv` files:

- **Center Modal Family (`<DataImportModal>`)**: Follows `ProductFormModal.tsx` standards (`centered`, `fullScreen={isMobile}`, default cancel / blue primary buttons, plain text title).
- **Client-Side Extraction & Validation (`fileParser.ts`)**: Parses uploaded spreadsheets client-side via SheetJS before transmitting to the server. Evaluates required columns, case-insensitive header aliases, custom row validators, and data transformations with instant visual preview.
- **Preflight Preview, Row Selection & Data Grid**: Full-width scrollable data grid with sticky row checkboxes, row numbers, and status badges. Allows users to selectively check/uncheck rows (master select-all with indeterminate state, "Select All Valid", "Deselect All") so only selected valid data is imported. Displays all configured columns without header clipping, formatted currency (`formatMoney`) and numeric values right-aligned, monospace barcodes, real-time search, status filter tabs (`All`, `Selected`, `Valid`, `Issues`), and selectable page sizes (10, 25, 50).
- **Automatic Category Identification & Styling View (`CategoryStylingView.tsx`, `categoryDetector.ts`)**: Automatically discovers distinct categories and subcategories from parsed files, matches them with catalog entries, auto-assigns rotating palette colors and smart contextual icons, and offers a dedicated styling view where users can fine-tune colors and icons using `TablerIconPicker` and color swatches before saving.
- **Template Generation (`templateGenerator.ts`)**: Generates downloadable sample `.xlsx` (with auto-column widths) and `.csv` templates with prefilled example rows.
- **Server Audit & Processing**: Confirms import batch via `POST /api/imports`, pre-creating/updating customized categories with their custom colors & icons, invalidating relevant queries (`queryKeys.imports.all`, `queryKeys.categories.all`, `queryKeys.inventory.all`), and displaying server outcomes with expandable row-level error reports.
- **Config-Driven Extensibility (`ImportConfig`)**: Reusable across any module by providing an `ImportConfig` object (`target`, `columns`, `sampleRows`, `supportedOptions`). The inventory implementation is configured in `src/features/inventory/config/inventoryImportConfig.ts`.

## Release & Versioning Management

- **Automated Conventional Commit Versioning**: Pushes to `main` evaluate Conventional Commit prefixes via `scripts/ci/next-version.sh`.
  - `feat:` -> minor bump (`0.5.0` -> `0.6.0`)
  - `fix:` / `perf:` -> patch bump (`0.5.0` -> `0.5.1`)
  - `feat!:` or `BREAKING CHANGE:` -> minor bump (pre-1.0)
  - `chore:`, `docs:`, `ci:`, `refactor:`, `test:`, `style:` -> no bump
  - Release-worthy commits automatically trigger `node scripts/ci/set-version.mjs`, committing `chore(release): vX.Y.Z [skip ci]` and tagging `vX.Y.Z` on `main`.
- **Single Source of Truth**: `frontend/package.json`'s `version` field tracks this automated stream and is aligned with the desktop pos-compose repo's baseline (`0.5.0`). Root `scripts/set-version.py` also updates both manifests when pos-compose releases run.
- **Build Identity**: `vite.config.ts` bakes `__APP_VERSION__`, `__BUILD_TIME__`, and `__GIT_SHA__` into `src/config/env.ts`, and emits `dist/version.json`.
- **Environment Override**: `vite.config.ts` supports `VITE_APP_VERSION` environment variable to override `package.json` if explicitly provided during CI or Docker builds (`process.env.VITE_APP_VERSION?.trim() || pkg.version`).
- **Web CI Deployment (`.github/workflows/deploy.yml`)**: On push to `main`, the workflow executes `next-version.sh`, pushes the release commit/tag if bumped, and passes `VITE_APP_VERSION` and `VITE_GIT_SHA` as build-args to Docker.
- **Web PWA Intelligent Background Updates (`src/app/pwa/`)**:
  - `PwaUpdateContext.tsx` drives multi-trigger background update detection: immediate check on tab visibility (`visibilitychange`), window focus, network reconnection, and adaptive interval (60s while visible and active, 5m when backgrounded).
  - Version probing (`versionProbe.ts`): lightweight `fetch('/version.json', { cache: 'no-store' })` (< 150 bytes) detects new GitHub Actions deploys within seconds. If a commit or build timestamp difference is detected, `registration.update()` is called immediately to precache new assets.
  - Cart safety: `shouldOfferUpdate` ensures the cashier is never prompted or interrupted mid-sale (`cartItemsCount === 0`).
  - Bulletproof activation: `src/sw.ts` calls `clientsClaim()` on activation so that `self.skipWaiting()` causes open clients to immediately experience a `controllerchange` event, triggering clean window reload without requiring hard refresh (`Cmd+Shift+R`).
- **Updates Section UI (`UpdatesSection.tsx`)**:
  - Web displays `env.appVersion`, `env.buildTime`, and the short commit hash (`env.commit.slice(0, 7)`).
  - Desktop uses `isTauri()` gating and queries `@tauri-apps/api/app`'s `getVersion()` which resolves dynamically to the desktop bundle's version.

### Invariants & Rules for Future Implementations

- **Desktop Feature Isolation**: Any desktop-native capability (file system operations, backup/restore, auto-updater, window controls) must be gated using `isTauri()` and declared with `desktopOnly: true` in `settingsSections.ts`. Never assume Tauri APIs exist in standard browser environments.
- **PDF Rendering Standard**: Never render generated documents using raw browser `<iframe>` or `embed` tags. Always use `PdfCanvasViewer` to ensure consistent rendering across all platforms (desktop WebKit/WebView2 and browsers).
- **Modal & Layout Consistency**: Modals must adhere to the `ProductFormModal.tsx` design pattern: `centered`, `fullScreen={isMobile}`, plain text titles (no emoji/raw JSX in header titles), and consistent button ordering (Cancel on left, primary action on right). Responsive UI must use `useLayoutTier` or `useIsMobile`.
- **I18n Alphabetization**: All new user-facing strings must use `t('key')` and be added to `src/shared/i18n/dictionaries/si.json` in strictly alphabetical order without omitting translations.
- **State & Money Management**: All monetary values must remain integer cents throughout UI components (`unitPriceCents`, `totalCents`), formatted only at the presentation boundary via `formatMoney`. Never compute currency totals with floating-point arithmetic.
